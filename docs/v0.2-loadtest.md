# v0.2 秒杀策略性能测试

## 用途

`cmd/loadtest` 对真实 HTTP 秒杀接口发起并发请求，记录：

- 总耗时和吞吐量（QPS）。
- 创建成功、幂等重放、售罄、竞争繁忙、网络错误数量。
- min、avg、P50、P90、P95、P99、max 延迟。
- 每个请求的 HTTP 状态、业务码、是否重放、耗时和错误。

自动准备模式会创建商品、活动和大量测试用户，只能连接隔离测试数据库。

## 1. 选择服务端策略

修改 `etc/store-api.yaml`：

```yaml
Seckill:
  StockMode: atomic # atomic / pessimistic / optimistic
```

每次修改后重启服务：

```bash
go run . -f etc/store-api.yaml
```

启动日志会打印实际策略。压测参数 `-strategy` 只是报告标签，工具无法代替你确认服务端配置，因此标签必须与启动日志一致。

## 2. 执行独立用户压测

管理员必须拥有 `seckill:write` 权限。密码建议通过环境变量提供，避免写入 shell 历史：

```bash
export SERVICE_RPC_LOADTEST_ADMIN_EMAIL='admin@example.com'
export SERVICE_RPC_LOADTEST_ADMIN_PASSWORD='your-password'
```

Atomic：

```bash
go run ./cmd/loadtest \
  -strategy atomic \
  -scenario unique \
  -requests 1000 \
  -concurrency 100 \
  -stock 1000 \
  -run-id atomic-001 \
  -output docs/benchmark/v02-atomic.json
```

把服务端配置改为 `pessimistic` 并重启，然后保持其他参数不变：

```bash
go run ./cmd/loadtest \
  -strategy pessimistic \
  -scenario unique \
  -requests 1000 \
  -concurrency 100 \
  -stock 1000 \
  -run-id pessimistic-001 \
  -output docs/benchmark/v02-pessimistic.json
```

Optimistic 同理：

```bash
go run ./cmd/loadtest \
  -strategy optimistic \
  -scenario unique \
  -requests 1000 \
  -concurrency 100 \
  -stock 1000 \
  -run-id optimistic-001 \
  -output docs/benchmark/v02-optimistic.json
```

`unique` 会为每个请求准备独立用户，避免数据库唯一索引把后续请求变成幂等重放。注册和登录属于 setup 阶段，不计入正式 QPS。

`run-id` 用于报告分组和测试用户命名，可以重复使用；商品 SKU 会附加时间戳和进程内序号，
避免重复运行触发唯一索引冲突。为了区分不同轮次的报告，仍建议每轮使用清晰、不同的 `run-id`。
自动准备产生的数据不会由工具删除，建议使用可重建的独立测试库，并在测试结束后统一清理。

### 指定已有 SKU 和秒杀库存

传入 `-sku-id` 后，工具不会创建新商品，而是为该 SKU 自动创建并启用一场新的秒杀活动；
`-stock` 是这场活动为该 SKU 配置的秒杀库存：

```bash
go run ./cmd/loadtest \
  -strategy atomic \
  -scenario unique \
  -sku-id 123 \
  -stock 500 \
  -requests 1000 \
  -concurrency 100 \
  -run-id sku-123-atomic-001 \
  -output docs/benchmark/sku-123-atomic-001.json
```

注意：`sku-id` 是商品规格 ID，工具会创建新的秒杀 `item_id`；`item-id` 则表示直接压测已经存在的
秒杀项，因此 `-sku-id` 和 `-item-id` 不能同时指定。目标 SKU 必须存在且处于可用状态。

## 3. 幂等重放压测

```bash
go run ./cmd/loadtest \
  -strategy atomic \
  -scenario replay \
  -requests 1000 \
  -concurrency 100 \
  -stock 1000 \
  -run-id replay-001 \
  -output docs/benchmark/v02-replay.json
```

此场景所有请求使用同一用户，预期只有一个 `created`，其余为 `replayed`。它测试的是幂等读取路径，不代表真实抢购吞吐。

## 4. 使用已有 item 和 Token

每行一个 JWT：

```bash
go run ./cmd/loadtest \
  -strategy atomic \
  -scenario unique \
  -item-id 123 \
  -tokens-file /tmp/seckill-tokens.txt \
  -requests 1000 \
  -concurrency 100 \
  -output docs/benchmark/v02-existing-data.json
```

`unique` 至少需要与请求数相同的 Token；`replay` 只需要一个。

## 对比要求

- 三轮使用相同机器、MySQL、连接池、请求数、并发数和库存。
- 每种策略至少重复 3～5 轮，比较中位数，不以单次最好成绩下结论。
- 同时观察 `created` 是否等于预期库存，以及是否出现 `inventory_busy`、网络错误或其他错误。
- 当前工具测量客户端观察到的端到端延迟，不等价于数据库 SQL 执行时间。
- go-zero 的 `HTTP 503 + Request Timeout` 会统计为 `server_timeout`；空响应体或非 JSON 的
  `HTTP 503` 会统计为 `server_rejected`。二者分别表示慢请求超过服务端时限和请求被快速拒绝，
  不再混入 `CLIENT_ERROR`。非 JSON 响应还会在样本的 `response_body` 中保留最多 512 字节摘要。
- `MaxOpenConns`、CPU、磁盘和网络都可能成为瓶颈；只比较策略时不要同时修改这些变量。
