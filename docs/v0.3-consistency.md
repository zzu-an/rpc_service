# v0.3 Redis / MySQL 一致性诊断

v0.3 的 Redis 是准入资格，不是库存事实源。Redis Lua 成功后，MySQL 事务仍可能失败、超时或返回提交结果未知。因此两个存储允许出现一个保守方向的差值：Redis 剩余资格少于 MySQL 可售库存。

## 计数关系

对单个 item 定义：

```text
stock_delta       = mysql.available_stock - redis.stock
reservation_delta = redis.buyers - mysql.claims
```

正常状态下：

```text
redis.stock <= mysql.available_stock
redis.buyers >= mysql.claims
stock_delta == reservation_delta
```

差值为 0 是 `CONSISTENT`。差值大于 0 是 `RESERVED_AHEAD`，表示已有 Redis 资格尚未形成 MySQL claim，可能少卖，但没有凭空增加资格。

这只是瞬时计数关系，不是跨存储事务快照。它不能证明 buyer 与订单逐条对应，也不能替代 v0.6 的对账。

## 状态解释

- `CONSISTENT`：库存和已用资格计数一致。
- `RESERVED_AHEAD`：Redis 更保守；检查失败请求或提交未知请求，不自动修复。
- `CACHE_MISSING`：没有 state，购买路径应 fail closed；活动中禁止在线重建 buyers。
- `DANGEROUS_DRIFT`：Redis stock 高于 DB、buyers 越界、差值不等或 TTL 缺失，需要停止活动并人工分析。
- `UNKNOWN`：任一存储读取失败；工具不会把失败值伪装成 0。

## 故障矩阵

| 故障 | 当前行为 | 原因 |
|---|---|---|
| Lua 拒绝 | 不访问 MySQL | 保护热点行 |
| Lua 成功、MySQL 成功 | 两边各消费一份 | 正常提交 |
| Lua 成功、MySQL 明确失败 | 保留 buyer | 自动回补可能与并发重试交错 |
| MySQL Commit 结果未知 | 保留 buyer 和同一 orderNo | 重试通过唯一键读取赢家 |
| Redis 命令超时 | 不访问 MySQL、不重试 Lua | 超时不等于服务端未执行 |
| Redis key 丢失 | fail closed | 回源会把峰值压回数据库 |

## 使用

```bash
go run ./cmd/v03check -f etc/store-api.yaml -item <item-id>
```

命令只读取精确 item，不执行 `KEYS`、全表扫描或任何修复。退出码：一致/保守预留为 0，缓存缺失为 1，危险漂移/未知为 2。输出不会包含 DSN、Redis 地址或密码。
