# v0.3 缓存风险与热 key 实验

## 当前策略

### 缓存穿透

未知或未预热 item 在 Lua 中返回 `SECKILL_CACHE_NOT_READY`。Redis gate 没有 MySQL reader，领域服务在 gate 拒绝时也不会调用 MySQL Purchase，因此不存在购买请求的隐式回源。

### 缓存击穿

购买路径不做懒加载。管理员必须在活动开始前显式预热，state 的 TTL 覆盖 `end_at + grace + jitter`。这避免热点 key 到期瞬间由大量用户请求同时重建。

### 缓存雪崩

不同 item 根据 item ID 使用确定性、有界 jitter；同 item 重试得到相同绝对过期时间。state 与 buyers 共享逻辑过期点，不能一个存在、另一个提前丢失。

jitter 只能错开不同商品，不能解决同一个商品的热 key。

### 大 key

buyers 只在库存成功减一后写入；重复用户先返回原 orderNo，售罄用户不写字段，因此 `HLEN(buyers) <= initial_stock`。如果未来改成“所有访问用户都写标记”，这个上界会失效。

### 热 key

Lua 把多次网络往返合并成一次 O(1) 状态转换，但同商品 state/buyers 仍落在同一个 Redis shard。Redis 在 shard 内串行执行命令，长 Lua 会阻塞其他 key；当前脚本禁止扫描和循环。

Pipeline 只能减少预热网络往返，不让跨 item 写入自动获得事务语义。Cluster hash tag 只保证同 item 两个 key 同 slot，也不会自动分散单商品热点。

## 验证

```bash
TEST_REDIS_ADDR='...' TEST_REDIS_PASSWORD='...' go test -race ./internal/seckill/redisgate
TEST_REDIS_ADDR='...' TEST_REDIS_PASSWORD='...' go test -run '^$' -bench BenchmarkReserveHotItem -benchmem ./internal/seckill/redisgate
```

benchmark 固定访问一个 item，并在计时前加载脚本。结果只代表当前客户端、网络、Redis 配置和样本规模，不能直接写成生产 QPS 承诺。

## 剩余风险与后续归属

- 单 shard 热点、入口限流、本地 sold-out 标记：v0.7，需要先有当前基线。
- Redis Cluster/Sentinel 与故障切换：部署阶段单独验证。
- 活动中 key 丢失后的自动恢复：本阶段 fail closed；v0.6 结合订单/库存对账设计。
- 指标、slowlog、latency monitor、CPU 与网络观测：v1.0 可观测阶段。

当前版本宁可在依赖故障时少卖，也不通过自动回源或猜测库存扩大故障与超卖风险。
