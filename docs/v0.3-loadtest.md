# v0.3 Redis 准入对照压测

## 目的

使用完全相同的 HTTP 工作负载比较：

- `admission=mysql`：v0.2 所有请求直接进入 MySQL Purchase。
- `admission=redis`：v0.3 先执行 Lua，售罄/未预热请求不进入 MySQL Purchase。

工具保留逐请求样本并记录 QPS、P50/P90/P95/P99、业务码、最终 DB/Redis 状态。HTTP 客户端无法精确观察服务内部 Purchase 调用次数，该字段明确标为 unavailable；“售罄不调用 MySQL”由 TASK-027 的 spy 测试证明，不能用 claim 数冒充调用数。

## 固定变量

两轮必须保持以下内容一致：

- 机器与 Go 版本。
- MySQL/Redis 部署位置与连接池配置。
- `StockMode`、请求数、并发数、库存和客户端超时。
- unique/replay 用户模型。
- 除 `Seckill.AdmissionMode` 外的服务配置。

`-strategy` 和 `-admission` 都只是报告标签。每次测试前必须核对启动日志：

```text
with seckill stock mode atomic and admission mode redis
```

工具不会自动改配置或重启服务。

## Redis 模式自动准备

自动准备按以下顺序执行：

```text
创建未来开始的活动 → 添加 item → 启用 → 预热 → 创建用户 → 等待 start_at → 正式计时
```

等待属于 setup，不计入 QPS。这样避免把 `SECKILL_UNAVAILABLE` 混入性能样本。

## 执行

先以 mysql admission 启动服务：

```bash
go run ./cmd/loadtest \
  -admission mysql \
  -strategy atomic \
  -scenario unique \
  -requests 1000 \
  -concurrency 100 \
  -stock 100 \
  -redis-deployment remote-standalone \
  -run-id v03-mysql-001 \
  -output docs/benchmark/v03-mysql-001.json
```

只修改服务端 `AdmissionMode: redis` 并重启，其他参数保持相同：

```bash
go run ./cmd/loadtest \
  -admission redis \
  -strategy atomic \
  -scenario unique \
  -requests 1000 \
  -concurrency 100 \
  -stock 100 \
  -redis-deployment remote-standalone \
  -run-id v03-redis-001 \
  -output docs/benchmark/v03-redis-001.json
```

再分别执行 replay 场景，所有请求共享一个用户：

```bash
go run ./cmd/loadtest -admission redis -strategy atomic -scenario replay \
  -requests 1000 -concurrency 100 -stock 100 \
  -run-id v03-redis-replay-001 -output docs/benchmark/v03-redis-replay-001.json
```

管理员和测试用户密码通过环境变量提供，不写入命令或报告。自动准备会创建数据，只能用于隔离/开发环境。

## 报告检查

- unique：成功订单不超过 stock；Redis 模式售罄请求应主要表现为 `OUT_OF_STOCK`。
- replay：Redis stock/buyers 与 DB available/claims 都只变化一次，所有成功响应返回同一订单。
- `backend.mysql` 和 `backend.redis` 是正式压测结束后的瞬时只读值，不计入 benchmark 时长。
- `samples[].order_id/order_no` 用于直接核对 replay 是否始终指向同一订单；不要只看 `replayed` 数量。
- `environment` 自动记录硬件摘要、Go 版本、Redis 部署说明、脱敏服务配置和原始报告绝对路径。`-redis-deployment` 必须按实际环境填写。
- 任一后端不可读时字段保持缺失并记录 `error_categories`，不能伪装成 0。
- 至少重复 3～5 轮比较中位数；不以单轮最好值下结论。
- 网络 RTT、Redis 远近和 MySQL 连接池会显著影响结果，必须随原始 JSON 一起记录。

## 不能得出的结论

- 客户端 QPS 不是 Redis 或 MySQL 的理论上限。
- claim 数不是 MySQL Purchase 调用数。
- 单机测试不能证明 Cluster、主从切换或跨机房行为。
- Lua 降低数据库流量不等于消除了单 Redis shard 热点。
