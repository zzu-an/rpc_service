# v0.2 单机秒杀验收

## 本阶段解决的问题

v0.2 在保持单体、只使用 MySQL 本地事务的前提下，解决了并发扣库存、同步订单原子性和同一用户重复购买问题。

正式 HTTP 链路使用条件原子 UPDATE。悲观锁和乐观锁是内部可测试变体，不暴露给客户端选择。

## 运行前提

1. 准备与开发库隔离的 MySQL 数据库，例如 `service_rpc_test`。
2. 使用指向测试库的配置执行 migration，确认版本为 `6 dirty=false`。
3. 执行：

   ```bash
   make verify-v02 TEST_DSN='service_rpc:service_rpc_dev@tcp(127.0.0.1:3307)/service_rpc_test?charset=utf8mb4&parseTime=true&loc=UTC'
   ```

## 已验证行为

- 错误的“先查库存再无条件写回”可稳定出现业务放行数大于库存。
- 原子 UPDATE、`SELECT ... FOR UPDATE`、version CAS 均保持库存、订单和 claim 数量一致。
- 100 并发下三种策略均无超卖。
- 默认原子策略在 1000 并发下无超卖。
- 同一用户 100 个并发重放只创建一个订单并只扣一次库存。
- 真实 HTTP 链路完成注册、登录、管理员配置活动、首次购买和重复购买；重放返回相同订单 ID、订单号与 `created_at`。
- 活动禁用、未开始、已结束和库存售罄不会留下部分订单。
- migration 在隔离测试库完成 `5 → 6 → 5 → 6`，均为 `dirty=false`。
- race detector、vet 和阶段技术边界扫描通过。

## 关键结论

- 库存最终不为负不等于没有超卖，必须同时核对成功资格/订单数。
- 应用层“先查询重复订单”只是优化，数据库唯一索引才是并发幂等底线。
- 悲观锁用排队换确定性；乐观锁用 CAS 冲突和重试换较短持锁时间；应依据冲突率和延迟数据选择，不能凭名称判断优劣。
- 数据库热点仍然存在，是下一里程碑要回答的问题；本阶段不提前引入缓存或异步化。
