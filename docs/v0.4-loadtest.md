# v0.4 sync/async 对照压测

## 目的与口径

本报告比较相同硬件、数据规模、库存、并发和请求总数下的同步下单与 Kafka 异步下单。
它回答两个不同问题：

- `benchmark_duration_ms`、`throughput_qps` 和 latency 描述 HTTP 入口的接收能力；
- `drain_duration_ms` 与 `final_*` 描述入口停止后，worker 将已接收任务处理到终态的速度。

两组数字不能相加或互相替代。异步模式降低的是入口等待重事务的时间并限制 Purchase
的同时执行数量，并不减少每笔订单所需的 SQL；job 持久化、发布状态更新和 offset 提交反而会
增加总 I/O。结果仅对本次环境和参数有效，不是生产容量承诺。

## 可复现命令

服务端分别使用 `Seckill.OrderMode: sync` 与 `Seckill.OrderMode: async`，其余参数保持一致。
async 还需同时启动 `cmd/seckill-worker`。以下命令中的账号、密码和服务地址必须通过本地环境
提供，不写入报告或仓库：

```bash
go run ./cmd/loadtest \
  -url http://127.0.0.1:8888 \
  -config etc/store-api.yaml \
  -strategy atomic -admission redis \
  -order-mode async \
  -scenario unique \
  -concurrency 100 -requests 1000 -stock 100 \
  -drain-timeout 60s -poll-interval 200ms \
  -redis-deployment remote-standalone \
  -output docs/benchmark/v04-async.json
```

同步组只把 `-order-mode` 改为 `sync`，并使用同步模式配置启动 API。两个模式应使用新建且
结构相同的活动，避免上一轮库存和用户幂等记录污染下一轮。

## 报告字段解释

- `http_202/queued`：请求已写入持久化 job 表，不代表订单已经创建；
- `final_succeeded`：结果查询已看到订单，是最终成功的事实来源；
- `final_failed`：任务经过明确失败路径进入终态；
- `final_pending`：排空窗口结束时仍为 QUEUED，不能直接解释为丢单；
- `result_poll_error`：轮询期间最后一次查询失败，需结合 worker、Kafka 和数据库检查；
- `replayed`：同一用户/商品的幂等重试，共享同一 `order_no`；工具按唯一订单号轮询，避免查询风暴。

## 面试与优化点

入口 P99 下降不等于端到端耗时下降。评估削峰系统至少要同时观察入口延迟、Kafka lag、排空
时间、终态成功率以及 Purchase 峰值并发。当前工具为保证实现清晰，按轮次顺序轮询唯一订单；
超大规模压测可改成带并发上限和随机抖动的批量轮询，或由服务提供批量结果接口，但不能让
结果查询流量反过来压垮数据库。

Kafka consumer lag 是 offset 差值，不等于失败订单数；offset 已提交但 job 状态更新滞后、
重试 topic 中的消息以及尚未发布的 job 都需要单独观察。`cmd/v04check` 的多后端读数也不是
原子快照，因此报告必须保留采集时间和原始 JSON，不能伪造瞬时强一致结论。

## 本次结果

执行时间为 2026-08-29，客户端为 darwin/arm64、10 个逻辑 CPU、Go 1.26.1；API
运行在本机，MySQL/Redis/Kafka 均为 `192.168.0.107` 测试环境。两组均使用 atomic、
Redis admission、100 并发、1000 请求、100 库存和独立的新活动。

| 指标 | sync | async |
|---|---:|---:|
| HTTP 入口耗时 | 2852.41 ms | 262.68 ms |
| 入口吞吐 | 350.58 req/s | 3806.90 req/s |
| 平均入口延迟 | 163.59 ms | 25.71 ms |
| P95 | 1591.20 ms | 179.26 ms |
| P99 | 2592.71 ms | 223.90 ms |
| 已接收 | 100 个 200/订单 | 100 个 202/job |
| 售罄 | 900 | 900 |
| 最终成功 | 100 | 100 |
| 排空耗时 | 不适用 | 4532.38 ms |
| 最终失败/仍排队 | 0/0 | 0/0 |
| MySQL 库存/claim | 0/100 | 0/100 |
| Redis 库存/buyer | 0/100 | 0/100 |

本次 async 入口吞吐约为 sync 的 10.86 倍，P99 约降至 1/11.58；但 async 还需要
4.53 秒后台排空，所以不能表述为“订单端到端快 11 倍”。阶段门禁另外用真实 Kafka 验证
Purchase 峰值不超过配置的消费槽、停止消费时 topic offset 增长、恢复后 group lag 归零。
压测报告中的 `mysql_purchase_calls_available=false` 表示通用 HTTP 工具没有侵入生产代码采集
峰值；该指标由 stage 测试包装仓储采集，不能在 JSON 中伪造一个数字。
