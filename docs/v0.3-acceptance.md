# v0.3 Redis 准入阶段验收

## 本阶段结论

v0.3 在 v0.2 MySQL 正确性防线之前增加 Redis Lua 准入：未预热、Redis 故障、售罄请求 fail closed，不进入 MySQL Purchase；获得资格后仍由 MySQL 本地事务、条件库存更新和唯一购买记录决定最终订单。

它解决的是“售罄流量仍争用数据库热点行”，没有解决 Redis 与 MySQL 的原子提交。Lua 成功而 MySQL 失败时保留 Redis 预留，因此 Redis 剩余资格可能低于 MySQL 可售库存，表现为少卖而不是超卖。自动回补资格可能把结果未知但实际已成功的资格再次放出，当前阶段明确禁止。

## 验收环境

- 客户端：darwin/arm64，10 logical CPU，Go 1.26.1。
- MySQL：一次性 `mysql:8.0` 容器、隔离数据库；门禁结束后容器已删除。
- Redis：LAN 上的 standalone 实例，测试仅使用带唯一 item ID 的 key；不记录认证信息。
- 服务：单进程，atomic stock mode；两轮只切换 admission mode。

完整门禁入口：

```bash
make verify-v03 \
  TEST_DSN='指向隔离 MySQL 的 DSN' \
  TEST_REDIS_ADDR='Redis 地址' \
  TEST_REDIS_PASSWORD='按实例需要提供'
```

`TEST_DSN` 和 `TEST_REDIS_ADDR` 缺失会直接失败。门禁先在隔离库执行 migration `up → down → up`，再执行全量 race；集成测试不得以 skip 伪造通过。

## 正确性证据

- 真实 Redis 的 1000 个独立用户争抢 100 库存：100 次预留、900 次售罄，最终 stock=0、buyers=100。
- 真实 MySQL + Redis 的 1000 并发：100 个订单、100 条 claim，两个存储的剩余库存均为 0。
- 同用户 100 并发：只创建 1 个订单，Redis 只扣 1 次，所有响应恢复同一订单号。
- Redis 售罄、key 缺失、断连时领域 spy 断言 MySQL Purchase 调用为 0。
- Lua 成功而 MySQL 失败时不执行 Redis 回滚；`v03check` 将该保守差值报告为 `RESERVED_AHEAD`，不在线修复。
- 分布式锁只存在于 `labs/distributed-lock`；生产源码引用扫描为 0。

## 同负载 HTTP 报告

本次报告保留全部逐请求样本。以下数字只描述这次本机客户端、隔离 MySQL 与 LAN Redis 的组合，不能视为容量承诺：

| admission / 场景 | 请求 / 并发 / 库存 | 结果 | QPS | P50 / P95 / P99 |
|---|---:|---|---:|---:|
| mysql / unique | 1000 / 100 / 100 | 100 created，900 sold out | 897.71 | 76.949 / 308.808 / 452.816 ms |
| redis / unique | 1000 / 100 / 100 | 100 created，900 sold out | 1487.36 | 12.218 / 445.679 / 636.492 ms |
| redis / replay | 100 / 100 / 100 | 1 created，99 replayed | 920.48 | 81.975 / 105.215 / 106.560 ms |

原始数据直接引用，不在本文复制或手改样本：

- `docs/benchmark/v03-mysql-20260827.json`
- `docs/benchmark/v03-redis-20260827.json`
- `docs/benchmark/v03-redis-replay-20260827.json`

Redis unique 报告末态为 DB stock=0、claims=100、Redis stock=0、buyers=100。replay 报告末态为两边 stock=99、claims/buyers=1，且成功样本的 `order_no` 去重后只有一个值。HTTP 报告无法观察进程内部 Purchase 精确调用数，因此 `mysql_purchase_calls_available=false`；“售罄不回源”由 spy 集成测试证明，不能用 claim 数替代。

单轮结果中 Redis unique 的吞吐更高，但其 P95/P99 并未全面优于 MySQL，说明网络 RTT、连接池、服务日志和尾延迟会改变结论。正式容量判断至少重复 3～5 轮并比较中位数。

## 缓存风险与边界

- 穿透：不存在 item 直接返回 cache-not-ready，不懒加载数据库。
- 击穿：活动前显式预热；购买链路不重建丢失 key。
- 雪崩：活动结束后保留短 TTL，并按 item 加确定性有界 jitter。
- 热 key：Lua 将状态转换压缩为一次 O(1) 脚本，但单商品仍是单 shard 热点。
- 大 key：buyers 只记录获得资格的用户，字段数不超过初始库存。
- Cluster：两个 key 使用同一 hash tag；本阶段没有宣称已验证集群切换。

## 注释质量审查

重点注释均解释“为什么”和失败边界，而非逐行翻译：Lua O(1) 与 shard 阻塞、`NOSCRIPT` 仅重载一次、超时不盲目重试、启停活动的失效顺序、同一 UTC 时间、保守预留不回滚、TTL jitter 的能力边界、claim 不等于 Purchase 调用数、锁 TTL 双持有者与 fencing token。面试点和后续优化点均留在对应实现附近，便于从代码追到约束。
