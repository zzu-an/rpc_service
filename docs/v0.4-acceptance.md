# v0.4 阶段验收

## 结论

v0.4 阶段门禁通过。HTTP 202 只在 job 持久化后返回，Outbox Relay 使用 Kafka
`RequireAll` 确认发布，consumer 采用 Fetch→Handle→Commit 的至少一次流程；重复发布和
消费由 `order_no`、claim 和 job 条件状态更新吸收。订单表仍是最终事实源。

## 验收环境

- MySQL：`192.168.0.107:3307/service_rpc` 测试库，migration latest 为 v8；
- Redis：`192.168.0.107:6379`；
- Kafka：`192.168.0.107:9092`，阶段测试使用每轮唯一 topic/group；
- 客户端：darwin/arm64，10 logical CPU，Go 1.26.1。

凭据没有写入本文或 JSON 报告。用户已明确说明整台 `192.168.0.107` 为测试环境，因此门禁
在该库执行 v8→v7→v8 迁移往返并写入唯一前缀的阶段数据。

## 真实链路证据

- 1000 个不同用户竞争库存 100：100 个 job 获得资格，900 个明确售罄；
- 同一用户并发重试 100 次：始终返回首次 `order_no`，只保留一个 job；
- Kafka 发布失败：job 保持 pending；恢复后继续发布；
- broker ack 后 MySQL 状态更新失败：允许重复发布，不先确认、不丢 job；
- 主消息、retry、poison→DLQ 均通过真实 Kafka；瞬时 Fetch 错误会退避恢复；
- 100 个 job 最终全部 SUCCEEDED，库存 0、claims 100、buyers 100；
- 成功后重复发布同一事件 100 次，订单、claim 和库存保持不变；
- consumer 启动前 topic offset 已增长，处理后 main group lag 为 0；
- Purchase 峰值并发不超过阶段配置的 consumer slot；
- 其他用户查询同一 `order_no` 统一返回不存在，不能枚举订单。

## 对照压测

同为 1000 请求、100 并发、库存 100，sync 创建 100 笔订单、900 售罄；async 接受 100
个 job、900 售罄，随后 100 个全部成功，排空 4532.38ms。async 入口为 3806.90 req/s、
P99 223.90ms；sync 为 350.58 req/s、P99 2592.71ms。详细口径与原始样本见
[v0.4-loadtest.md](v0.4-loadtest.md)。结论只说明本次环境下入口削峰有效，不声称总 SQL
减少，也不把入口延迟当端到端延迟。

## 验收中发现并修复的问题

1. MySQL JSON 会规范化文本，原始字节比较把首次 job 误判为 payload 漂移；现按保留数字精度
   的 JSON 语义比较。
2. 并发重放没有恢复首次 reserved_at；现从服务端生成的赢家订单号确定性恢复毫秒时间。
3. 多 producer 重复建 topic 把 `TopicAlreadyExists` 当失败；现只忽略该明确幂等结果。
4. kq 的 sync push 仍使用 `RequireNone`，不能证明 broker ack；现直接配置 kafka writer 为
   `RequireAll`、同步写、BatchSize=1、Hash balancer。
5. reader 遇到一次 Fetch 错误会永久退出；现运行期退避重试，关闭时单独停止 fetch 并给在途
   消息保留优雅处理预算。

## 阶段边界

生产目录未新增 RPC/etcd、支付状态机、自动补偿/对账、系统级限流、分布式事务或完整观测
平台。Redis 与 MySQL 之间的残余少卖窗口、Kafka 与 MySQL 的跨系统原子性仍按 ADR-003
明确保留，后续里程碑不能把它们描述为 exactly-once。
