# AGENTS.md

本文件约束所有 AI Coding Agent（Codex / Claude Code / Cursor / 其他代理）在本项目中的行为。

## 1. 总原则

你不是“自由重构代理”，而是“受约束的实现代理”。

任何代码修改都必须满足：

1. 先阅读：
   - `ROADMAP.md`
   - `ARCHITECTURE.md`
   - 当前阶段 `docs/specs/<version>.md`
   - 当前任务 `docs/tasks/<task>.md`
2. 只实现当前任务，不自动开始下一个任务。
3. 不允许为了“更优雅”做与任务无关的大范围重构。
4. 不允许提前引入后续阶段技术。
5. 不允许隐式扩大修改范围。
6. 修改公共接口、跨层依赖、数据库 schema、消息格式、RPC IDL、第三方依赖前，必须先说明理由。
7. 优先最小可工作的修改。
8. 所有实现必须可验证。

## 2. 开始编码前必须输出

在修改任何文件前，先输出：

- 当前任务目标
- 计划修改的文件
- 预计新增文件
- 是否涉及公共接口变更
- 是否涉及数据库/schema 变更
- 是否涉及外部依赖
- 验证方式

如果任务需要修改 5 个以上现有文件，先停止，说明是否应该拆任务。

## 3. 严格禁止

除非当前 TASK 明确允许，否则禁止：

- 新增中间件
- 引入新的 Web 框架
- 修改 RPC 协议
- 修改消息格式
- 新增数据库表
- 修改已有表含义
- 跨服务直接访问数据库
- 为“以后可能需要”提前抽象
- 创建没有当前调用方的接口层
- 同时重构多个 package
- 重命名大量文件
- 一次性替换核心组件
- 把单体阶段提前改成微服务
- 把同步流程提前异步化
- 把 MySQL 方案提前替换成 Redis
- 为了“性能”做无 benchmark 支撑的优化

## 4. 分阶段技术隔离

必须遵守 `ROADMAP.md` 中的阶段边界。

例如：

- v0.1 禁止 Redis / MQ / RPC / etcd
- v0.2 禁止 Redis / MQ / RPC / etcd
- v0.3 才允许 Redis / Lua / 分布式锁
- v0.4 才允许 MQ
- v0.5 才允许 gRPC / Protobuf / etcd
- v0.6 才重点处理最终一致性、补偿、对账
- v0.7 才引入系统级限流、降级、隔离
- v1.0 才集中做观测、容器化、压测和故障演练

若 Agent 认为必须提前引入，必须停止编码并提交架构变更建议，不得直接实现。

## 5. 完成任务前必须执行

至少完成以下验证：

- 编译
- 单元测试
- 当前任务指定的测试
- 静态检查（若项目已有）
- 必要时 benchmark / integration test

如果无法运行测试，要明确说明：
- 哪些没跑
- 为什么没跑
- 风险是什么

## 6. 完成后输出固定格式

### 修改摘要
- ...

### 修改文件
- `path`: 原因

### 验证结果
- `command`: PASS / FAIL

### 公共接口变化
- 无 / 有，说明

### 遗留问题
- 无 / ...

### 是否建议进入下一任务
- 是 / 否
- 原因

## 7. Architecture Gate

以下情况必须先做 ADR，再编码：

- 新增 Redis / MQ / RPC / etcd / ES 等基础设施
- 改数据库事务模型
- 改幂等策略
- 改服务边界
- 改库存扣减模型
- 改消息投递语义
- 改一致性模型
- 引入新的缓存一致性方案
- 引入熔断 / 限流 / 隔离机制
- 影响两个以上核心模块的公共抽象

ADR 模板见 `templates/ADR_TEMPLATE.md`。

## 8. Task Size Gate

一个 TASK 推荐：

- 修改 1～5 个现有文件
- 新增 0～3 个文件
- 1 个明确能力
- 1 个明确验收标准
- 30 分钟～半天内可完成

超过这个范围，优先拆分。

## 9. 学习优先规则

这个项目不是“尽快堆技术栈”，而是“理解系统演进”。

任何技术引入都必须回答：

1. 当前瓶颈是什么？
2. 不引入它会怎样？
3. 它解决了什么？
4. 它引入了什么新问题？
5. 如何验证它真的有效？

无法回答时，不应引入。
