# v0.5 RPC 故障预算与重试矩阵

## 冻结矩阵

| 链路 | 总预算 | 单跳预算 | RPC 最大尝试 | 外层重投 | 最坏调用放大 |
|---|---:|---:|---:|---:|---:|
| Gateway → 普通写 RPC | 1000ms | 300ms | 1 | 无 | 1 |
| Gateway → Get/Find RPC | 1000ms | 300ms | 1 | 无 | 1 |
| Stream task | 700ms | inventory 250ms；order 350ms | 各 2 | PEL 最多 8 delivery | 每个写 RPC 最多 16 次 |
| Order Outbox → Kafka | 非 HTTP 链路 | broker 3000ms | 每次 claim 1 | Outbox 退避重试 | 无固定总次数，事件 ID 稳定 |
| Kafka → notification | consumer operation 3000ms | DB context 继承 consumer | 每次 delivery 1 | retry/DLQ 最多 3 delivery | DB 最多 3 次，event_id 收敛 |
| Kafka → projector | consumer operation 3000ms | Redis 500ms | 每次 delivery 1 | retry/DLQ 最多 3 delivery | Redis 最多 3 次，event_id 收敛 |

Gateway 的 Get/Find 当前保持一次尝试：规范允许“至多一次”额外重试，并不要求默认开启。这样先把 Stream
consumer 的两层放大控制清楚，避免 gateway、zRPC 和业务 adapter 同时各重试三次形成 retry storm。

## 故障结论

- timeout 限制一次调用占用资源的时间；retry 恢复短暂抖动；breaker 在连续依赖失败后快速拒绝。三者都不提供业务幂等。
- 只有 `DeadlineExceeded` 与 `Unavailable` 计入 breaker 并允许幂等调用重试。售罄、参数错误、NotFound、冲突等业务返回说明服务可达，不会打开 breaker。
- inventory/order 秒杀写 RPC 复用稳定 `order_no` 并逐字段校验重放载荷，因此最多两次 RPC 尝试是安全的。普通订单创建与注册没有客户端幂等键，固定一次。
- retry 同时受父 context 剩余时间、最大尝试数、指数退避+jitter 限制。父 deadline 到达时，退避 timer 与调用必须立即结束。
- order-rpc 模拟延迟 3 秒时，100 次调用均按 20ms 测试 deadline 返回，goroutine 不随请求数线性增长；停止服务同样在调用方预算内失败。
- inventory 注入 50% 首次 `Unavailable` 时，100 个业务请求严格执行 150 次 RPC attempt，并以稳定 key 收敛为 100 个事实。
- 真实 etcd 测试发现两个 zRPC endpoint；etcd 不可达时调用有界失败，不回退静态 endpoint。服务实例摘除与慢实例结论在 TASK-069 多进程生命周期验收继续验证。

## 明确禁止

- breaker 打开后不得直连其他服务 MySQL，也不得从 gateway 装配本地 repository。
- timeout 后不得换新 `order_no` 重试；响应丢失不能证明服务端未提交。
- 不为追求“成功率”在每一层开启默认三次重试；必须先计算上述最坏放大倍数。
