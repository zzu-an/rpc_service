# ADR-001: v0.2 库存与订单采用单个 MySQL 本地事务

## 状态

Accepted

## 背景

v0.1 已有通用订单与订单项，但没有库存语义。v0.2 需要在并发下同时保证库存不超卖、订单不重复和失败可回滚，并且阶段边界禁止 Redis、MQ、RPC 与分布式事务。

## 决策

1. 新增 `seckill_activities`、`seckill_items` 和 `seckill_order_claims`。
2. 秒杀订单复用 `orders`、`order_items`，不复制订单模型。
3. 库存扣减、订单快照写入和购买记录写入由秒杀持久化适配器在一个 MySQL 事务内完成。
4. 正式 HTTP 链路使用条件原子更新：

   ```sql
   UPDATE seckill_items
   SET available_stock = available_stock - 1
   WHERE id = ? AND available_stock > 0;
   ```

   影响行数为 0 表示库存不足或目标不存在，随后以受控查询区分业务错误。
5. 悲观锁方案使用 `SELECT ... FOR UPDATE`；乐观锁方案使用 `version` CAS 和有限次数重试。两者用于当前阶段教学、验证与对比，不暴露给 HTTP 客户端动态选择。
6. 数据库唯一约束 `UNIQUE(activity_id, seckill_item_id, user_id)` 负责并发下防止重复购买。发生唯一键冲突时，当前事务回滚，再读取第一次成功请求创建的订单作为幂等结果。

## 原因

- 单个本地事务提供 v0.2 所需的原子性，失败路径清晰且能用真实 MySQL 验证。
- 条件更新避免“查询库存后再更新”的时间窗口，同时比给整个请求加 Go Mutex 更接近多实例前的正确数据库模型。
- 唯一索引是并发幂等的最终防线；应用层预查询只能优化常见路径，不能提供互斥保证。
- 同时保留三种库存策略，可以比较锁竞争、CAS 冲突和吞吐取舍，而不污染外部协议。

## 代价

- 秒杀持久化适配器会协调库存表和订单表，事务职责较重。
- 热点商品仍会形成数据库热点；这是 v0.2 有意保留并在 v0.3 解决的问题。
- 乐观锁在高冲突下可能耗尽重试并返回竞争错误，不能承诺每个有库存请求最终都成功。

## 被否决方案

- Go 进程内 Mutex：无法覆盖未来多实例，且进程崩溃时不提供事务原子性。
- 分布式锁、Redis Lua：违反 v0.2 阶段边界。
- MQ 异步下单：会提前引入最终一致性和消息可靠性问题。
- 单独建立完整秒杀订单表：复制 v0.1 订单模型，增加不必要的数据分叉。

## 验证

- 100/1000 并发库存与订单不变量测试。
- 同一用户并发重放测试。
- 三种正确库存策略分别通过集成测试和 race detector。
- 测试专用错误方案可复现竞态，但不能被正式程序引用。
