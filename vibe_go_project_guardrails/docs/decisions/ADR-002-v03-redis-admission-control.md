# ADR-002: v0.3 采用 Redis 准入预留，MySQL 保持最终事实源

## 状态

Accepted

## 背景

v0.2 的 MySQL 本地事务能够保证库存和订单正确，但活动请求量远大于库存时，所有请求都会访问同一库存行和数据库连接池。v0.3 需要用 Redis 把绝大多数无资格请求挡在数据库之前，同时阶段边界禁止 MQ、分布式事务和微服务化。

Redis 预扣与 MySQL 订单事务无法原子提交。如果不先冻结事实源、失败策略和重试标识，常见的“Redis 减一失败就加回去”会在超时或提交结果未知时放出重复资格。

## 决策

1. MySQL 继续保存最终库存、订单和唯一购买记录；Redis 不是事实源。
2. Redis 保存活动开始前生成的短生命周期快照，并作为 MySQL Purchase 之前的准入层。
3. 单个 Lua 脚本按“ready/时间 → 重复用户 → 库存 → 扣减并标记”的顺序执行。
4. buyer 标记保存第一次生成的 `order_no`。重试和并发重放都使用同一个订单号进入现有 MySQL 幂等事务。
5. Redis 拒绝、缺 key 或故障时不回退 MySQL，采用 fail closed 保护热点数据库。
6. Lua 已成功而 MySQL 失败、超时或提交结果未知时，保留 Redis 预留；本阶段接受少卖，不自动回补造成潜在超卖。
7. Redis/DB 差异只做只读诊断，不在 v0.3 在线修复。补偿和对账留给 v0.6。
8. 预热只允许在活动启用且开始前执行；活动中 Redis 数据丢失后停止放行，不在线重建 buyers。
9. 下单链路不用分布式锁。锁只在独立 lab 中用于学习 token、compare-and-delete、TTL 失效和 fencing token。
10. 不修改 v0.2 数据库 schema，不移除 MySQL 条件更新和唯一索引。
11. Redis 客户端直接使用 go-zero 已依赖的 `go-redis/v9`。当前 go-zero 封装不暴露 `Close` 且不支持逻辑 DB；显式生命周期和 DB 配置优先于便捷封装，具体类型仍限制在 infrastructure/redisgate 内。
12. 同一 buyer 的并发重放复用 orderNo，MySQL 中 `orders.order_no` 或购买 claim 任一唯一冲突都进入“读取已提交赢家”分支；只有按 user+item 确实读到订单才返回幂等成功。

## 候选方案

### 方案 A：Redis 准入，MySQL 最终提交（已选）

优点：

- 售罄请求不进入数据库，直接针对当前热点问题。
- 复用 v0.2 已验证的事务与唯一索引，正确性边界清晰。
- 同步 HTTP 成功响应仍然包含已提交订单，不提前引入异步状态。

缺点：

- 两个存储无法原子提交，失败时可能保守少卖。
- Redis 故障时秒杀入口不可用。
- 获得 Redis 资格的请求仍然需要访问 MySQL。

### 方案 B：Redis 作为最终库存，MySQL 只写订单

优点：

- MySQL 不再扣热点库存行，路径更短。

缺点：

- 改变库存事实源和 v0.2 事务模型，需要新的持久化、恢复和对账语义。
- 无 MQ 时 Redis 成功、MySQL 失败没有可靠续传机制，超出 v0.3 边界。

### 方案 C：Redis 故障时回退 MySQL

优点：

- Redis 故障期间表面可用性更高。

缺点：

- 故障瞬间会把全部峰值重新压到热点数据库，可能把局部故障放大成系统故障。
- 两条入口同时存在时更难解释资格和库存差异。

### 方案 D：给整个下单流程加分布式锁

优点：

- 表面上容易理解为“同一时刻只让一个请求执行”。

缺点：

- 串行化热点商品，吞吐和尾延迟恶化。
- 锁 TTL、进程暂停和网络分区仍会产生并发持有者。
- 锁不能让 Redis 与 MySQL 形成共同事务。

## 为什么选择当前方案

- 它只解决 v0.2 已经证明存在的数据库热点，不提前解决 MQ 或最终一致性阶段的问题。
- 它把“正确订单”继续交给 MySQL，把“是否值得访问 MySQL”交给 Redis，职责单一。
- fail closed 和保留未知预留让失败方向保持保守：可能少卖，但不会为了可用性盲目放出重复资格。
- 同一个 `order_no` 同时是 Redis 预留标识和 MySQL 幂等恢复线索，能处理响应丢失与提交结果未知。

## 代价

- Redis 成为秒杀入口的强依赖，需要明确的 503 语义和故障演练。
- Redis 剩余资格可能小于 MySQL 可售库存，需要差值报告和人工判断。
- v0.3 不能承诺活动库存全部售出，也不提供在线自动修复。
- 单商品 Redis key 仍可能成为 shard 热点；本阶段测量并记录，完整热点治理留给 v0.7。

## 验证方式

- 真实 Redis 并发运行 Lua，证明库存和 buyer 标记原子变化。
- MySQL + Redis 联合测试 1000 并发/100 库存与同用户重放风暴。
- 注入 Redis 缺 key、断连和结果未知，证明不会回退 MySQL。
- 注入 MySQL 失败或提交结果未知，证明不自动回补 Redis，且同 order_no 可重试恢复。
- 同一 HTTP 工作负载比较 v0.2 与 v0.3 的 MySQL Purchase 调用数和延迟分布。

## 回滚策略

- 启动配置可显式切回 `Seckill.AdmissionMode=mysql`，用于回滚和 v0.2 对照压测。
- 回滚必须通过重启完成并记录实际模式，不能在单个请求级别动态绕过 Redis。
- Redis 新 key 具有 TTL，可停止写入后自然过期；不修改 MySQL schema 和既有订单数据。
