# v0.1 单体商城 Spec

## 1. 阶段问题

项目已经通过 `labs/` 学习了部分 Go 并发与 gRPC 基础，但还没有一条完整、可运行的商城业务链路。v0.1 先解决单体应用中的接口组织、数据持久化、身份认证、权限校验和本地事务问题，为后续研究库存并发建立正确的业务基线。

> 本阶段只证明“基础业务在单体和 MySQL 中能够正确运行”。它不证明系统具备秒杀、高并发或分布式能力。

## 2. 目标

完成一个基于 go-zero REST API 和 MySQL 的模块化单体，提供：

- 用户注册、登录和当前用户信息查询。
- JWT 身份认证。
- 基于角色和权限码的 RBAC。
- 商品及 SKU 的基础管理、列表和详情查询。
- 不涉及库存的基础订单创建和订单详情查询。
- 可重复执行、可回退的数据库 migration。
- 覆盖登录、权限和订单事务边界的自动化测试。

## 3. 非目标

以下能力明确不属于 v0.1：

- Redis、任何形式的分布式缓存和缓存一致性处理。
- MQ、异步下单、延迟消息和事件驱动。
- RPC、gRPC 业务服务、Protobuf 业务协议和 etcd。
- 秒杀活动、库存查询、库存扣减、防超卖和库存回滚。
- 分布式锁、接口幂等、限流、熔断、降级和隔离。
- Refresh Token、Token 黑名单、主动踢下线和多设备会话管理。
- 支付、退款、物流、订单超时关闭和订单状态机。
- Docker Compose、Kubernetes、Prometheus 和分布式链路追踪。

`labs/grpc-deadline` 等阶段 0 实验可以继续存在，但 v0.1 的商城业务代码不得依赖它们，也不得使用 gRPC/Protobuf 实现模块间调用。

## 4. 技术边界

### 4.1 允许

- go-zero REST API。
- MySQL。
- JWT Access Token。
- 自适应密码哈希算法，例如 bcrypt。
- RBAC。
- 基础 handler/logic/domain/repository 分层。
- 单个 MySQL 数据库内的本地事务。
- 仅服务于正确性验证的单元测试和 MySQL 集成测试。

### 4.2 禁止

- Redis、MQ、RPC、etcd、分布式锁。
- 为后续阶段提前创建没有当前调用方的 cache、mq、rpc 接口或目录。
- 以性能为理由加入没有 benchmark 支撑的缓存或并发优化。
- 在订单流程中加入任何库存语义。

## 5. 架构与依赖方向

v0.1 是一个进程内运行的模块化单体。依赖方向必须保持：

```text
HTTP handler
    ↓
application logic
    ↓
domain rule
    ↓
repository interface
    ↓
MySQL implementation
```

约束：

- handler 只负责协议转换、参数接收和响应输出，不直接执行 SQL。
- logic 组织用例和本地事务，不依赖 HTTP request/response 类型。
- domain 不依赖 go-zero 或 MySQL driver。
- MySQL 实现不得泄漏数据库模型到 HTTP API。
- 不为以后拆微服务提前增加 RPC façade 或跨模块网络调用。

## 6. HTTP API 契约

统一前缀为 `/v1`。除注册、登录、商品公开查询和健康检查外，其余接口都需要有效 JWT。

### 6.1 运行状态

| Method | Path | 认证 | 说明 |
|---|---|---|---|
| GET | `/healthz` | 否 | 仅表示进程可接收请求，不承诺所有下游健康 |

### 6.2 用户与认证

| Method | Path | 认证 | 说明 |
|---|---|---|---|
| POST | `/v1/auth/register` | 否 | 使用邮箱和密码注册用户 |
| POST | `/v1/auth/login` | 否 | 校验凭证并签发 Access Token |
| GET | `/v1/users/me` | 是 | 返回当前登录用户的基本信息和角色 |

认证边界：

- JWT 至少包含 `sub`、签发时间和过期时间；`sub` 表示用户 ID。
- JWT 不保存权限列表。否则管理员调整角色后，旧 Token 会在过期前继续携带旧权限。
- 密码只保存自适应哈希结果，日志和响应不得包含明文密码、密码哈希或完整 Token。
- Token 缺失、格式错误、签名错误或过期均视为未认证。
- v0.1 只支持短期 Access Token，不提供 Refresh Token 和主动撤销能力。

### 6.3 RBAC 管理

| Method | Path | 认证/权限 | 说明 |
|---|---|---|---|
| PUT | `/v1/admin/users/:userId/roles` | JWT + `rbac:manage` | 替换指定用户的角色集合 |

RBAC 规则：

- 身份认证与权限校验是两个独立步骤。
- 未提供有效身份返回 HTTP 401。
- 身份有效但缺少所需权限返回 HTTP 403。
- 业务用权限码授权，例如 `rbac:manage`、`product:write`；不得在各 handler 中散落 `role == "admin"` 判断。
- 角色、权限及两者的关联以 MySQL 数据为准。v0.1 不增加 Redis 或进程内权限缓存。

### 6.4 商品

| Method | Path | 认证/权限 | 说明 |
|---|---|---|---|
| GET | `/v1/products` | 否 | 分页查询已上架商品 |
| GET | `/v1/products/:productId` | 否 | 查询已上架商品及其有效 SKU |
| POST | `/v1/admin/products` | JWT + `product:write` | 创建商品及初始 SKU |
| PUT | `/v1/admin/products/:productId` | JWT + `product:write` | 更新商品基础信息 |
| PUT | `/v1/admin/products/:productId/status` | JWT + `product:write` | 上架或下架商品 |

商品规则：

- 商品列表使用 `page` 和 `page_size`，默认值由实现任务固定，`page_size` 必须设置上限。
- 公开查询不能返回下架商品。
- 商品写接口只管理商品资料和 SKU 售价，不管理库存。
- 金额一律使用整数分，例如 `price_cent: 1999` 表示 19.99 元；禁止用浮点数保存或计算金额。

### 6.5 基础订单

| Method | Path | 认证 | 说明 |
|---|---|---|---|
| POST | `/v1/orders` | 是 | 根据一个或多个 SKU 创建基础订单 |
| GET | `/v1/orders/:orderId` | 是 | 查询当前用户自己的订单详情 |

订单规则：

- 客户端只提交 SKU ID 和购买数量，不提交可信成交价或订单总金额。
- 服务端从 MySQL 读取当前有效 SKU 价格，计算明细小计和订单总金额。
- 订单保存商品名、SKU 描述、单价和数量快照，后续商品改名或改价不能改变历史订单。
- 订单头与全部订单明细必须在同一个 MySQL 本地事务内创建；任意明细失败时整个事务回滚。
- 用户只能查询自己的订单；不得通过修改 ID 读取他人订单。
- v0.1 **不查询、不锁定、不扣减库存**。数量只做正整数及合理上限校验。
- v0.1 不承诺重复请求只创建一笔订单；接口幂等属于后续并发阶段。

## 7. 统一响应与错误语义

成功与失败均使用稳定的 JSON 外壳：

```text
{
  "code": "稳定的机器可读代码",
  "message": "面向调用方的简短说明",
  "data": "成功时为业务数据，失败时为空",
  "request_id": "用于关联日志的请求标识"
}
```

重点错误映射：

| HTTP | code | 语义 |
|---:|---|---|
| 400 | `INVALID_ARGUMENT` | 参数格式或业务输入不合法 |
| 401 | `UNAUTHENTICATED` | 未提供有效身份 |
| 401 | `TOKEN_EXPIRED` | Token 已过期；仍属于未认证 |
| 403 | `PERMISSION_DENIED` | 已认证但无权限 |
| 404 | `USER_NOT_FOUND` | 用户不存在 |
| 404 | `PRODUCT_NOT_FOUND` | 商品不存在或公开场景下不可见 |
| 404 | `ORDER_NOT_FOUND` | 订单不存在或不属于当前用户 |
| 409 | `USER_ALREADY_EXISTS` | 邮箱唯一约束冲突 |
| 409 | `ROLE_ASSIGNMENT_CONFLICT` | 角色集合不合法或关联冲突 |
| 500 | `INTERNAL_ERROR` | 未预期错误，不向客户端泄漏 SQL、堆栈或内部路径 |

同一种业务失败在不同 handler 中必须返回相同的 HTTP 状态和业务 code。数据库错误需要在 repository/logic 边界转换，不能把 driver 错误文本直接暴露给客户端。

## 8. 数据契约

本节固定后续 migration 的业务含义；TASK-001 不创建数据库表。

### 8.1 用户与权限

- `users`
  - 邮箱唯一。
  - 只保存密码哈希。
  - 状态字段用于禁止无效用户登录。
- `roles`
  - 角色 code 唯一且稳定，展示名称可以变化。
- `permissions`
  - 权限 code 唯一且稳定。
- `user_roles`
  - `(user_id, role_id)` 唯一，禁止重复授予。
- `role_permissions`
  - `(role_id, permission_id)` 唯一，禁止重复关联。

### 8.2 商品

- `products`
  - 保存商品基础资料和上/下架状态。
- `product_skus`
  - 隶属于一个商品。
  - SKU code 在约定业务范围内唯一。
  - 售价使用 `BIGINT` 整数分，必须非负。
  - 不包含库存字段；库存模型留到后续阶段定义。

### 8.3 订单

- `orders`
  - 订单号唯一。
  - 关联下单用户。
  - 总金额使用 `BIGINT` 整数分。
  - v0.1 只需要表达“已创建”的基础状态，不提前设计支付或补偿状态机。
- `order_items`
  - 关联订单和下单时的 SKU。
  - 保存商品/SKU 文本、单价、数量和小计快照。
  - 小计等于单价乘数量，订单总金额等于全部小计之和。

所有表的具体字段类型、索引和外键由对应 schema TASK 在此语义范围内确定。任何新增表或改变上述含义的行为，都必须先更新任务范围；不得在实现中隐式扩展。

## 9. 注释要求

后续实现需要对不直观的业务约束写清楚“为什么”，重点包括：

- JWT 不携带权限快照的原因。
- 401 与 403 的判断边界。
- 密码及 Token 的日志脱敏规则。
- migration 中唯一约束和联合索引保护的业务不变量。
- 金额使用整数分而不是浮点数的原因。
- 订单本地事务的开始、提交和回滚边界。
- 订单为何刻意不包含库存语义。
- 测试所复现的越权、约束冲突或事务回滚场景。

不要给生成代码、简单赋值、明显的条件分支添加逐行翻译式注释。公共接口和存在重要前置条件的函数应提供 GoDoc。

## 10. 验收场景

### 10.1 用户与认证

- 新用户注册成功，数据库中不存在明文密码。
- 相同邮箱重复注册得到 `USER_ALREADY_EXISTS`。
- 正确凭证可以登录；错误密码不暴露用户是否存在等额外信息。
- 缺失、篡改和过期 Token 均不能访问受保护接口。

### 10.2 RBAC

- 普通用户访问管理接口得到 403。
- 具备 `rbac:manage` 的用户可以调整角色。
- 角色调整后，后续请求依据数据库中的最新权限结果授权。

### 10.3 商品

- 公开列表只返回上架商品，并遵守分页上限。
- 下架或不存在的商品不能通过公开详情接口读取。
- 只有具备 `product:write` 权限的用户可以写商品。

### 10.4 订单

- 服务端依据 SKU 当前价格计算订单金额，忽略客户端伪造金额。
- 多明细订单中任一明细无效，订单头和其他明细全部回滚。
- 用户不能读取其他用户的订单。
- 创建订单不会读取或修改任何库存字段。

### 10.5 Migration 与质量门禁

- 空数据库可以执行全部 migration。
- migration 再次执行时为安全的无操作。
- 当前版本 migration 可以按任务定义回退。
- 所有测试、race 检查和静态检查通过。

## 11. 验证命令

每个实现 TASK 需要运行自身指定的测试。v0.1 最终至少运行：

```bash
go test ./...
go test -race ./...
go vet ./...
```

MySQL migration 和集成测试命令在数据库基础 TASK 中固定；测试必须使用隔离的测试数据库，不得连接生产数据库。

## 12. Definition of Done

- 核心 API 可运行，并符合本 Spec 的认证和错误语义。
- migration 可重复执行，且存在明确回退路径。
- 登录、JWT、RBAC 和越权场景有自动化测试。
- 订单创建的本地事务提交与回滚均得到验证。
- `go test ./...`、`go test -race ./...`、`go vet ./...` 通过。
- 商城业务代码没有使用 Redis、MQ、RPC、etcd 或分布式锁。
- 能说明 v0.1 解决了单体业务正确性，同时明确库存并发仍是 v0.2 要回答的问题。

## 13. ADR 判断

当前 Spec 不要求 ADR。go-zero API、MySQL、JWT、RBAC 和单库本地事务都在 v0.1 已批准的技术边界内。

如果实现过程中希望提前加入 Redis/RPC、改变订单事务模型、加入库存扣减或引入跨模块公共抽象，应停止当前 TASK，先提交架构变更建议；满足 Architecture Gate 时必须先写 ADR。
