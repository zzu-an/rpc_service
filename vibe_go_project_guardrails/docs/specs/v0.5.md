# v0.5 微服务治理与 Kafka 领域事件 Spec

## 1. 阶段定位

v0.1～v0.4.2 的工作中心是“高并发秒杀系统”：先保证 MySQL 库存正确，再用 Redis Lua
削峰，最后用 Redis Stream 完成原子异步入队和 PEL 恢复。

v0.5 从提交 `b4a7b03`、分支 `codex/v0.4.2-redis-stream` 开始第二条项目主线：

> 构建一个数据所有权明确、同步 RPC 可治理、异步事件可重放、局部故障不会无限扩散的微服务系统。

秒杀不再决定全部架构；它只是最苛刻的业务样本，用于验证 RPC deadline、幂等、积压、局部失败和
数据库保护。普通用户、商品、订单和通知链路同样属于本阶段验收范围。

相关决策：

- `docs/decisions/ADR-005-v05-rpc-service-boundaries.md`
- `docs/decisions/ADR-006-v05-kafka-domain-events.md`

## 2. 当前问题与改进目的

| 当前问题 | v0.5 改进 | 为什么值得 |
|---|---|---|
| HTTP、业务和全部 repository 在同一进程 | 拆分 RPC 服务和 gateway | 建立真实部署/故障/数据边界 |
| 服务可直接跨领域 JOIN | 每个服务只访问自有数据 | 避免分布式单体 |
| 本地调用没有远程失败语义 | deadline、cancel、幂等重试、熔断 | 防止慢依赖拖垮调用方 |
| Redis Stream worker 直接写 MySQL | 改为秒杀编排 worker 调用 inventory/order RPC | 保护服务数据所有权 |
| 订单成功后下游只能同步耦合 | Order Outbox→Kafka 领域事件 | 下游失败不回滚订单，支持独立消费和重放 |
| Kafka 只有技术栈名称，没有真实下游 | notification-service + seckill result projector | 验证 consumer group fan-out、幂等和故障隔离 |

本阶段不以“进程越多”或“中间件越多”为目标。每一跳必须有明确的所有权、可靠性或性能理由。

## 3. 本阶段目标

1. 保持现有外部 HTTP 契约，由无数据库连接的 `gateway-api` 转发到业务 RPC。
2. 拆出 `user-rpc`、`product-rpc`、`seckill-rpc`、`inventory-rpc`、`order-rpc`、
   `notification-rpc`。
3. 使用 Protobuf/zRPC 和 etcd；所有跨进程调用有明确 deadline、错误分类和取消传播。
4. Redis Lua+Stream 保持为 seckill-service 内部的原子准入/短期队列，不为了接 Kafka增加中转跳数。
5. Stream worker 不再直接写订单库，而是幂等调用 inventory-rpc 和 order-rpc。
6. order-rpc 在本地事务中写订单与 Outbox，由 relay 可靠发布 `order.created.v1`。
7. notification-service 与 seckill result projector 使用不同 consumer group 消费同一订单事件。
8. 重复 RPC、重复 Kafka 事件和提交结果未知时不重复扣库存、建单或创建通知。
9. 服务发现异常、RPC timeout、Stream PEL、Kafka lag 和 Outbox backlog 可通过日志/诊断命令观察。

## 4. 非目标

- 不做库存自动释放、定时补偿、自动对账、Saga、TCC；这些属于 v0.6。
- 不做完整订单库背压、系统级限流、隔离仓、热点分桶、自动扩容；这些属于 v0.7。
- 不做 Prometheus/Grafana/OpenTelemetry/Kubernetes；这些属于 v1.0。
- 不接真实短信、邮件或推送供应商；notification 先提供站内通知和可替换 sender 接口。
- 不创建 payment/coupon/recommendation 等没有当前调用方的服务。
- 不物理拆分 MySQL 集群；先建立逻辑表所有权和 repository 边界。
- 不承诺端到端 exactly-once；依赖至少一次投递和业务幂等。
- 不把 `codex/v0.4.1-kafka` 整分支 merge/cherry-pick，也不恢复旧
  `seckill_order_jobs` command/outbox 热路径。
- 不实现 Redis Stream→Kafka Bridge。只有后续证明 Redis 积压/故障域/多消费者能力不足时才重新评估。

## 5. 总体架构

```text
client
  │ HTTP / JWT
  ▼
gateway-api
  ├── user-rpc
  ├── product-rpc
  ├── seckill-rpc
  ├── order-rpc
  └── notification-rpc

所有 RPC 服务 → etcd 注册发现

秒杀内部异步面：
seckill-rpc → Redis Lua + Stream → seckill-orchestrator
                                      ├── inventory-rpc.ReserveSeckillStock
                                      └── order-rpc.CreateSeckillOrder

通用事件面：
order-rpc → Order DB（order + outbox 同事务）
          → order-outbox-relay
          → Kafka order.created.v1
              ├── seckill-result-projector consumer group
              └── notification-service consumer group
```

建议进程：

```text
cmd/gateway-api/
cmd/user-rpc/
cmd/product-rpc/
cmd/seckill-rpc/
cmd/inventory-rpc/
cmd/order-rpc/
cmd/notification-rpc/
cmd/seckill-orchestrator/
cmd/order-outbox-relay/
cmd/seckill-result-projector/
cmd/notification-consumer/
```

继续使用单一 `go.mod`，保留现有领域 package，按任务增加 adapter；不一次性搬迁整个目录树。

## 6. 服务与数据所有权

| 服务 | 拥有的数据 | 主要职责 |
|---|---|---|
| user-rpc | users、credentials、RBAC | 注册、认证、身份与权限 |
| product-rpc | products、product_skus | 商品管理、公开查询、SKU 快照 |
| seckill-rpc | activities、Redis state/buyers/Stream/results | 活动、预热、原子准入、结果投影 |
| inventory-rpc | seckill_items、inventory_reservations | 冻结商品快照、MySQL 库存预留 |
| order-rpc | orders、order_items、order_outbox_events | 普通/秒杀订单与订单事件 |
| notification-rpc | notifications、notification_consumptions | 站内通知写入与用户查询 |

v0.5 可仍位于同一 MySQL 实例，但每个进程只装配自己的 repository。移除跨服务外键和跨域 JOIN；
外部 ID 是引用，不代表可以查询对方表。服务内部外键继续保留。

### 6.1 秒杀商品冻结快照

创建秒杀 item 时，通过 product-rpc 获取并冻结 SKU ID、名称、编码和整数分价格。异步落单不重新读
实时商品价格，避免积压期间变价导致同一幂等键出现不同订单载荷。

### 6.2 库存预留账本

`seckill_inventory_reservations` 以 `order_no` 和 `(activity_id,item_id,user_id)` 唯一键兜底。
`ReserveSeckillStock` 在一个本地事务内完成条件扣减与 reservation 插入；同 key 同载荷重试返回原结果，
同 key 不同载荷返回冲突。

### 6.3 通知数据

`notifications` 保存 user_id、业务类型、标题、正文、关联 order_no、创建/已读时间。
`notification_consumptions.event_id` 唯一，防止 Kafka 重投生成重复通知。通知服务不能查询订单表；事件载荷
必须包含生成通知需要的最小不可变事实。

## 7. RPC 治理

### 7.1 Protobuf

- package/go_package 带 v1；字段号不复用，删除字段使用 `reserved`。
- ID 使用 uint64，金额使用整数分，时间单位全契约统一。
- enum 0 值为 UNSPECIFIED；RPC DTO 与 DB/HTTP DTO 隔离。
- 生成代码不手改，兼容解释写在 `.proto` 和手写 adapter。
- 内部错误映射成稳定 code，不透传 SQL、DSN、token、消息正文或堆栈。

### 7.2 Deadline、重试与熔断

- 总预算先于单跳预算；禁止 adapter 使用 `context.Background()` 截断取消。
- Get/Find 可在剩余预算内至多一次退避+jitter 重试。
- ReserveStock/CreateSeckillOrder 只有在唯一键和载荷冲突校验完成后才允许重试。
- 注册、普通订单创建、商品/活动写操作默认不自动重试。
- 参数、权限、售罄等业务错误不计入熔断；timeout/unavailable 才是依赖失败。
- consumer 重试和 RPC client 重试共同计算最坏放大倍数，禁止每层默认重试 3 次。
- 熔断打开只快速失败，不能回退跨库直连或本地 repository。

## 8. 秒杀内部异步链路

```text
POST 秒杀
  → gateway → seckill-rpc
  → Redis Lua：活动/重复/库存/buyer/XADD
  → HTTP 202 QUEUED

seckill-orchestrator
  → XREADGROUP / XAUTOCLAIM
  → inventory-rpc.ReserveSeckillStock(order_no,...)
  → order-rpc.CreateSeckillOrder(order_no,frozen_snapshot)
  → 成功后 XACK + XDEL
```

- Stream 是 seckill-service 内部实现，orchestrator 不直接访问 inventory/order 数据库。
- order 成功、XACK 前崩溃会重投；两个写 RPC 均必须幂等。
- inventory 成功、order 最终失败可能少卖，记录 `reserved_without_order`，不在 v0.5 自动回补。
- poison Stream message 进入 Stream DLQ 后再 ACK；临时错误保留 PEL。
- HTTP 202 只代表 Redis 已接受任务，不代表订单成功。

## 9. Kafka 领域事件

### 9.1 为什么 Kafka 放在订单成功之后

Kafka 用于“订单已经创建”这一跨服务事实，而不是为了给 Stream 和 RPC 中间增加一跳：

- 订单服务不需要等待通知或秒杀结果服务在线。
- 不同 consumer group 各自消费、积压和恢复，互不提交对方 offset。
- 未来真实出现 payment/analytics 等调用方时可继续订阅，无需修改订单事务。
- Kafka 不进入 HTTP/Redis 准入关键路径，不增加秒杀入口 P99。

### 9.2 Order Outbox

order-rpc 本地事务：

```text
BEGIN
  INSERT orders
  INSERT order_items
  INSERT order_outbox_events
COMMIT
```

relay 扫描未发布事件，等待 broker ack 后条件标记 published。broker ack 后、状态更新前崩溃允许重复发布；
下游必须以 event_id 幂等。不能先提交订单再直接 best-effort 发 Kafka。

### 9.3 order.created.v1

最小字段：event_id、event_type、schema_version、order_no、user_id、order_source、total_amount_cent、
created_at_ms。消息不携带密码、JWT、完整用户资料或可从自己数据库读取的内部 row。

Kafka key 使用 `order_no`；主 topic 为 `order-created-v1`，retry/DLQ 仍属于该事件流。

### 9.4 下游一：seckill-result-projector

- 只处理 `order_source=SECKILL`。
- 以 event_id 幂等更新 Redis result=SUCCEEDED。
- 结果查询始终先问 order-rpc；订单存在优先于滞后的 Redis 状态。

### 9.5 下游二：notification-service

- 使用独立 consumer group，收到每一条 order.created，而不是与 projector 竞争消息。
- 一个本地事务写 consumption ledger 和站内通知。
- 同 event_id 重投只产生一条通知；未知版本/坏消息进 DLQ。
- 通知 DB/发送失败只形成自己的 retry/lag，不回滚订单、不阻塞 projector。
- notification-rpc 提供当前用户通知列表/已读接口，gateway 不直接查通知表。
- v0.5 的 sender 只做站内通知；外部短信/邮件通过接口隔离但不实现假集成。

## 10. 外部 HTTP

保留现有认证、商品、订单、秒杀接口；新增：

```text
GET /v1/notifications
PUT /v1/notifications/:notificationId/read
```

JWT 在 gateway 解析，向 RPC 只传播必要 user_id/request_id。RPC timeout/unavailable 映射稳定
503/504，不能泄漏 gRPC 内部文本。gateway 不打开 MySQL/Redis/Kafka 连接。

## 11. 配置与生命周期

- 每个 RPC server 配置 listen、etcd hosts/key；每个 client 显式 timeout。
- Redis 只提供给 seckill 相关进程，Kafka 只提供给 relay/consumers。
- MySQL 配置按服务拆分，进程不能获得不需要的数据权限。
- 空 service key、非正 timeout/concurrency、重复 topic、consumer group 缺失必须启动失败。
- 退出时 RPC 先停止接流量；Stream/Kafka consumer 先停止拉取，再有限等待在途。
- 未 ACK/未 commit 的消息必须留给恢复，不能在 shutdown timeout 后假装成功。

## 12. 关键中文注释要求

重点代码必须解释“为什么、失败窗口、面试点”，至少覆盖：

1. v0.5 是治理中心，秒杀只是验证场景。
2. 同库为什么仍禁止跨服务 JOIN。
3. Stream 为什么留在 seckill 内部，以及为什么本阶段不加 Stream→Kafka Bridge。
4. worker 为什么必须调用 RPC，不能复用其他服务 repository。
5. deadline 如何传播，哪些操作可重试，最坏调用放大倍数。
6. 业务错误为什么不能误触发熔断。
7. order 与 outbox 为什么同事务，broker ack 未知为什么会重复事件。
8. Kafka 不同 consumer group 如何实现 fan-out，而不是负载均衡竞争同一条消息。
9. notification event_id 唯一键为什么是重复消费的最终防线。
10. 通知失败为什么不能回滚已成功订单。
11. inventory reservation/order create 为什么仍存在跨服务一致性窗口。
12. 查询为何先读订单事实，再读 Redis 投影。
13. 优雅退出时未确认消息如何恢复。

不要逐行翻译字段、循环或序列化代码；注释应帮助学习者解释架构取舍。

## 13. 验证

### 13.1 服务边界

- gateway 无数据库/MQ依赖；六个服务只访问自有表。
- 静态扫描禁止跨服务 repository/SQL 和跨服务外键。
- 所有服务通过 etcd 发现；实例停止、慢节点和 etcd 暂时不可用有界失败。

### 13.2 秒杀链路

- 1000 并发/库存 100：Redis buyer、MySQL reservation/order 不超过 100。
- 同用户 100 并发：一个 order_no、一条 reservation、一笔订单。
- 同 Stream task 重放 100 次：库存只减一次、订单只创建一次。
- order-rpc 延迟/不可用不会让 worker 无限阻塞，PEL 可恢复。
- `reserved_without_order` 可制造、可诊断，但没有自动补偿。

### 13.3 Kafka 与通知

- order 与 outbox 同事务；订单提交后 Kafka 停止不会丢失待发布记录。
- relay broker ack 后、标记前崩溃会重复事件，下游仍各产生一个事实。
- projector 和 notification 使用不同 group，均收到同一 order.created。
- notification consumer 停止时只增长自己的 lag；projector 继续工作，订单不受影响。
- 同事件重放 100 次只产生一条通知；poison event 进 DLQ 后后续消息继续。
- 用户只能查询/标记自己的通知。

### 13.4 门禁

- `go test -race ./...`、`go vet ./...`、IDL 兼容检查、migration up/down/up、`git diff --check`。
- 真实 MySQL、Redis、Kafka、etcd 验收；缺少参数必须失败，不能 silent skip。
- 边界扫描禁止 Stream→Kafka Bridge、旧 seckill job/outbox、自动补偿/对账、系统级限流和 v1.0 技术。

## 14. 本阶段不解决但必须记录的容量问题

队列只能削平峰值，不能提高订单库的真实处理能力。当多个活动或大库存导致 Stream 生产速率长期大于
order-rpc/MySQL 安全吞吐时，backlog 会持续增长。

v0.5 必须记录：Stream 长度/PEL、最老消息年龄、orchestrator 并发、order-rpc P99、DB 连接池等待、
Outbox backlog、Kafka consumer lag；但不在本阶段实现自动限流。

这些指标将把 v0.7 的问题具体化为“订单库保护与背压”，触发项包括：

- 按压测得到的 DB 安全吞吐限制 worker 并发/速率。
- 普通订单与秒杀订单使用独立 worker/连接池预算，避免互相饿死。
- backlog 年龄超过阈值时停止继续接受资格或执行可解释降级。
- 防止 RPC/client/consumer 多层重试形成重试风暴。
- 只有 Stream 内存、保留期、跨团队订阅或跨故障域需求被指标证明后，才评估 Kafka command queue/Bridge。

本节只记录下一阶段问题和触发条件，不创建 v0.7 代码或 TASK。

## 15. v0.5 运行实例规划

微服务要求的是独立进程和故障边界，不要求 v0.5 立即完成容器编排。以下数量既可以由本地进程实现，
也可以由用户后续按“一进程一容器”运行；Dockerfile、Compose 和 Kubernetes 仍留在 v1.0。

### 15.1 日常开发拓扑

| 类型 | 进程/实例 | 数量 | 说明 |
|---|---|---:|---|
| Edge | gateway-api | 1 | HTTP/JWT/RPC adapter，不连 DB/MQ |
| RPC | user-rpc | 1 | etcd key `service-rpc/user.v1` |
| RPC | product-rpc | 1 | etcd key `service-rpc/product.v1` |
| RPC | seckill-rpc | 1 | etcd key `service-rpc/seckill.v1` |
| RPC | inventory-rpc | 1 | etcd key `service-rpc/inventory.v1` |
| RPC | order-rpc | 1 | etcd key `service-rpc/order.v1` |
| RPC | notification-rpc | 1 | etcd key `service-rpc/notification.v1` |
| Worker | seckill-orchestrator | 1 | Redis Stream consumer group |
| Worker | order-outbox-relay | 1 | 发布 order.created |
| Consumer | seckill-result-projector | 1 | 独立 Kafka group |
| Consumer | notification-consumer | 1 | 独立 Kafka group |

应用进程合计 11 个。基础设施使用 MySQL、Redis、Kafka、etcd 各 1 个实例，合计 4 个；完整日常拓扑
共 15 个进程/实例。MySQL 可共享物理实例，但使用服务级配置/账号和逻辑表权限，不等于允许跨服务 SQL。

### 15.2 治理验收拓扑

在日常拓扑上只增加两个代表性副本：

| 进程 | 数量 | 验证目的 |
|---|---:|---|
| order-rpc | 2 | etcd 多 endpoint、负载均衡、慢节点、kill、滚动重启、幂等换实例重试 |
| notification-consumer | 2 | 同 group 分区分配、rebalance、单实例停止后恢复、重复消费幂等 |
| 其他应用进程 | 各 1 | 避免无收益地把所有服务复制一遍 |
| MySQL/Redis/Kafka/etcd | 各 1 | 集群高可用和容器编排不属于 v0.5 |

治理验收拓扑为 13 个应用进程 + 4 个基础设施实例，共 17 个。`order-created-v1` topic 至少 2 个
partition，确保两个 notification consumer 都能实际分配工作；projector 使用另一 group，仍会消费完整事件流。

### 15.3 明确不做的实例扩张

- 不把所有 RPC 都复制为 2～3 个；order-rpc 足以代表验证无状态 RPC 多实例治理。
- 不搭 3 节点 MySQL、Redis、Kafka 或 etcd；主从、ISR、quorum 和自动故障转移留给后续工程化。
- 不在 v0.5 创建 Kubernetes、Service Mesh、自动扩缩容或完整 Docker Compose。
- 实例数不是性能目标；扩副本前必须先证明下游数据库预算允许，否则只会放大连接与重试压力。

### 15.4 必做多实例实验

1. 两个 order-rpc 使用相同 etcd service key、不同 endpoint 注册。
2. 正常流量同时到达两个实例且外部契约一致。
3. kill 一个 order-rpc 后调用在 deadline 内转移到健康实例，不跨库回退。
4. 一个 order-rpc 注入 3 秒延迟，观察 timeout/熔断/错误率和 goroutine，不允许无限重试。
5. 两个 notification consumer 使用同 group；停止一个后 partition rebalance 到另一个。
6. projector 使用不同 group，与 notification group 同时收到同一 order.created。
7. 滚动重启 order-rpc 两个实例，幂等请求不重复建单。
