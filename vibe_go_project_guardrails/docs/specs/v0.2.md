# v0.2 单机秒杀 Spec

## 目标
在不引入 Redis/MQ 的前提下，用 MySQL 和 Go 并发控制解决单机秒杀正确性问题。

## 业务范围

- 管理员可以创建秒杀活动、配置一个活动下的 SKU 与库存，并启用或停用活动。
- 已登录用户可以在活动有效期内同步购买一个秒杀商品。
- 一个用户在同一活动的同一秒杀商品上最多成功一次。
- 重复请求返回已经创建的订单，不重复扣减库存。
- 秒杀订单继续写入 v0.1 的 `orders` 与 `order_items`，不建立第二套订单模型。

## HTTP 契约

```text
POST /v1/admin/seckill/activities
POST /v1/admin/seckill/activities/:activityId/items
PUT  /v1/admin/seckill/activities/:activityId/status
POST /v1/seckill/items/:itemId/orders
```

- 管理接口需要身份认证和 `seckill:write` 权限。
- 下单接口需要身份认证，每次请求只允许购买一个秒杀商品且数量固定为 1。
- 重放成功请求返回同一个订单，并用响应字段 `replayed` 标明是否为幂等重放。

## 数据与事务不变量

- `available_stock` 永远不能小于 0，也不能大于 `initial_stock`。
- `UNIQUE(activity_id, seckill_item_id, user_id)` 是防重复购买的最终数据库防线。
- 库存扣减、订单及订单项写入、购买记录写入必须位于同一个 MySQL 本地事务。
- 任何一步失败都必须整体回滚；请求超时不能直接推断事务失败。
- 正式 HTTP 链路默认使用带库存条件的原子 `UPDATE`。
- 悲观锁与乐观锁作为当前阶段的可验证实现保留，但不由外部请求选择策略。

## 错误语义

- `INVALID_ARGUMENT`：请求字段、时间范围或状态非法。
- `SECKILL_ACTIVITY_NOT_FOUND`：活动不存在。
- `SECKILL_ITEM_NOT_FOUND`：秒杀商品不存在。
- `SECKILL_UNAVAILABLE`：活动未启用、未开始或已经结束。
- `OUT_OF_STOCK`：库存不足。
- 重复购买不是系统错误；读取并返回第一次成功创建的订单。

## 核心学习
- 超卖
- 事务
- 行锁
- 乐观锁
- 幂等
- 并发测试

## 禁止
- Redis
- MQ
- RPC
- etcd

## 必须验证
- 100/1000 并发下库存不为负
- 成功订单数不超过库存
- 重复请求不会重复扣库存
- 原子更新、悲观锁与乐观锁方案分别通过并发正确性测试
- 错误的“先查后改”方案只能存在于测试中，并能稳定展示竞态问题
- migration 可升级、回退并重新升级
- race detector 通过

## 注释要求

关键代码必须使用中文解释设计原因和边界，至少覆盖：

- 事务内写入顺序和回滚语义。
- `RowsAffected`、`SELECT ... FOR UPDATE` 和 `version` CAS 的正确性依据。
- 唯一索引为何不能被业务层的“先查询”替代。
- 乐观锁重试上限、可重试错误和避免无限重试的原因。
- 请求超时、数据库提交结果未知时的幂等重试方式。

注释重点说明“为什么”，不为字段赋值、JSON 转换等显然代码逐行复述。
