# v0.4 MQ 异步化 Spec

## 背景

v0.3 已用 Redis Lua 把售罄和重复请求挡在 MySQL 事务之前，但每个获得资格的请求仍在 HTTP goroutine 内同步执行库存扣减、订单和 claim 写入。突发流量等于或接近库存时，MySQL 连接池、热点库存行和 HTTP 尾延迟仍会同时承压。

v0.4 只解决这个问题：把“资格已确认后的落单”变成可持久化、可重试的异步任务，以受控消费者并发削平 MySQL 峰值。相关决策见 `docs/decisions/ADR-003-v04-kafka-async-order.md`。

## 本阶段目标

- Redis Lua 继续负责资格和库存预扣，MySQL 继续作为订单与最终库存事实源。
- 获得资格后先幂等写入持久化投递记录，只有记录提交成功才返回 HTTP 202。
- 使用 Kafka 传输版本化落单消息，消费者以有界并发复用现有 MySQL Purchase 事务。
- 明确至少一次、重复投递、发送结果未知、消费失败、重试和死信语义。
- 提供用户侧结果查询，并让每个已返回 202 的请求最终可解释为 queued、succeeded 或 failed。
- 用相同工作负载比较 v0.3 同步落单和 v0.4 异步落单的入口延迟、MySQL Purchase 峰值并发与 backlog 排空时间。

## 非目标

- 不拆业务微服务，不引入 gRPC、Protobuf、etcd、服务发现或跨服务调用。
- 不追求端到端 exactly-once；Kafka 重投和进程崩溃都可能制造重复消息。
- 不修改支付/订单业务状态机，不做未支付自动关单或库存归还。
- 不做 Redis/MySQL 自动对账、自动补库存、Saga/TCC；这些属于 v0.6。
- 不做系统级限流、熔断、隔离、自适应扩缩容；这些属于 v0.7。
- 不接 Prometheus、Grafana、OpenTelemetry 或 Kubernetes；这些属于 v1.0。
- 不引入 RabbitMQ、RocketMQ 或第二种 MQ 主链路。

## 允许技术

- Kafka，开发环境 broker 为 `192.168.0.107:9092`。
- go-zero 官方 `github.com/zeromicro/go-queue/kq`，必要时使用其底层 `segmentio/kafka-go` 完成可确认发布和诊断。
- MySQL 持久化投递表（Outbox/Job Ledger）。
- 主 topic、retry topic 和 DLQ topic；三者仍属于同一个 Kafka 技术栈。
- 有界重试、退避、consumer group、offset、partition 和 lag 诊断。

## 禁止提前引入

- RPC / Protobuf / etcd。
- 分布式事务框架、TCC、Saga 和跨存储自动对账。
- 支付延迟队列、订单关闭状态机和库存自动回补。
- 系统级限流、熔断、隔离、热点分桶和自动扩缩容。
- 为未来微服务预建无调用方的接口或目录。

## 事实源与职责边界

- Redis 是资格准入层，buyer value 中第一次写入的 `order_no` 仍是整条链路的稳定幂等键。
- `seckill_order_jobs` 是“已接受异步请求”的持久化凭证和投递状态，不是库存或订单事实源。
- Kafka 是可重放运输日志，不是订单成功事实源。
- MySQL `orders`、`seckill_order_claims` 和 `seckill_items.available_stock` 仍是最终业务事实源。
- `orders.order_no` 与 `uk_seckill_claim_user_item` 是重复消费的最终正确性防线；内存标记、offset 或 Redis processed key 都不能替代数据库唯一约束。

## 核心流程

```text
POST 秒杀
  → Redis Lua Reserve
      ├── 拒绝：直接返回，不创建 job
      └── RESERVED / REPLAYED：取得稳定 order_no 与 reserved_at
  → MySQL EnsureJob(order_no, user_id, item_id, payload)
      ├── 首次：插入 PENDING_PUBLISH
      ├── 重放：返回原 job
      └── 失败：返回 503，保留 Redis 预留，不盲目回补
  → HTTP 202 QUEUED

worker relay
  → 扫描到期 PENDING_PUBLISH
  → 发布 Kafka 主 topic，key=order_no
  → broker 确认后条件更新 PUBLISHED
  → 若确认后进程崩溃，允许重复发布

Kafka consumer
  → 解码并校验 schema_version/event_type
  → 使用消息 reserved_at 执行 MySQL Purchase
      ├── 成功或已存在：job → SUCCEEDED，确认 offset
      ├── 可重试：可靠发布 retry topic 后确认源消息
      └── 不可重试/超限：可靠发布 DLQ、job → FAILED 后确认源消息
```

## 为什么 HTTP 不直接发送 Kafka

Kafka 暂时不可用时，若请求在 Redis 预扣后直接发送消息，应用只能选择返回错误并依赖用户重试，或错误地返回成功但丢失落单任务。v0.4 在二者之间增加持久化 job：HTTP 202 只承诺任务已写入 MySQL，relay 可在 Kafka 恢复后继续发布。

Redis Lua 与 MySQL job 插入仍不能组成原子事务。若 Lua 成功而 job 插入失败，服务返回 503 并保留资格；同一用户重试会从 Redis 取回同一个 `order_no` 并幂等补写 job。若用户永不重试，仍可能少卖；v0.4 必须如实记录该边界，不能用盲目 Redis 回滚制造超卖风险。

## 消息契约

主事件使用版本化 JSON，topic 建议：

```text
seckill-order-requested-v1
seckill-order-retry-v1
seckill-order-dlq-v1
```

必需字段：

- `event_id`：确定性取值 `seckill-order-requested:<order_no>`。
- `event_type`：固定 `seckill.order.requested`。
- `schema_version`：固定 `1`。
- `order_no`：Redis 首次预留保存的订单号。
- `user_id`、`item_id`。
- `reserved_at_ms`：Lua 接受资格时的 UTC 毫秒时间。
- `occurred_at_ms`：事件创建时间。
- `attempt`：主消息为 0，每次 retry 递增。

约束：

- Kafka message key 使用 `order_no`；同一请求的重复消息稳定落到同一 partition。
- 不按 `item_id` 分区，因为落单事务不要求 item 内严格顺序，把热 item 固定到单 partition 会限制消费并发。
- 消息不携带价格、商品名、库存结果或权限信息；消费者从 MySQL 事实源读取不可变订单快照。
- 新字段只能向后兼容增加；未知 schema version 进入 DLQ，不能猜测处理。
- 日志不得输出完整 payload、认证信息或 Kafka 密码。

## 数据模型变化

新增 `seckill_order_jobs`：

- `id`、`event_id`、`order_no`。
- `user_id`、`seckill_item_id`、`reserved_at`。
- `payload`，保存已冻结的版本化 JSON。
- `status`：`1=PENDING_PUBLISH, 2=PUBLISHED, 3=SUCCEEDED, 4=FAILED`。
- `publish_attempts`、`consume_attempts`、`next_publish_at`。
- `last_error_code`：只保存稳定分类，不保存带凭据/DSN 的原始错误。
- `published_at`、`completed_at`、`created_at`、`updated_at`。
- 唯一索引：`event_id`、`order_no`；到期扫描索引：`status,next_publish_at,id`；用户查询索引：`user_id,order_no`。

不修改 `orders.status` 的含义，也不新增支付状态。

## HTTP 契约变化

原路径保持：

```text
POST /v1/seckill/items/:itemId/orders
```

新增 `Seckill.OrderMode=sync|async`：

- `sync` 保留 v0.3 行为，仅用于回归和同负载对照。
- `async` 是 v0.4 正式模式，成功返回 HTTP 202：`order_no`、`status=QUEUED`、`replayed`。
- 未知模式必须启动失败，不能运行期根据 Kafka 错误回退同步 Purchase。

新增：

```text
GET /v1/seckill/orders/:orderNo/result
```

- 身份来自 Token，只能查询自己的 order_no。
- MySQL 已存在订单时返回 `SUCCEEDED` 和订单；该结果优先于可能滞后的 job 状态。
- job 为 FAILED 且订单不存在时返回 `FAILED`。
- 其他已接受状态统一返回 `QUEUED`，不伪造精确处理进度。
- 不存在或不属于当前用户统一返回 404，避免越权枚举。

## 投递和消费语义

- Relay 只扫描到期 pending job，发布成功后用条件更新标记 published。
- “发布成功、标记失败”会重复发布；消费者必须安全处理。
- 生产端错误按有界指数退避重新安排 `next_publish_at`，不能在紧循环内打满 broker/DB。
- 消费者必须使用 `reserved_at`，而不是消费时刻；backlog 可能跨过活动结束时间。
- 可重试错误包括受 context 约束的 MySQL 临时连接/事务错误；业务无效、坏消息和不支持版本不可重试。
- retry publish 未确认时不得确认源消息；结果未知允许重复 retry。
- 达到最大次数后先可靠写入 DLQ，再标记 FAILED，最后确认源消息。
- DLQ publish 成功后若状态更新/offset 提交失败，允许重复 DLQ；不能先确认源消息再尝试 DLQ。
- consumer group offset 不能作为业务幂等标记，因为进程可能在数据库提交后、offset 提交前崩溃。

## 并发和顺序边界

- 消费并发必须是显式正数配置，并小于 MySQL 连接池预算。
- Kafka 有效并行度同时受 partition 数和消费者数量限制；增加 goroutine 不一定提升吞吐。
- 当前订单扣减使用条件更新/唯一索引，不依赖同 item 严格顺序，所以不牺牲所有热 item 的并行度换取无用的全序。
- 优雅退出先停止拉取新消息，再给在途处理有限时间；未完成消息不能被假装成功确认，重启后允许重投。

## 可观测边界

本阶段提供命令行诊断而非完整监控平台，至少输出：

- job 各状态数量、最老 pending 年龄、发布失败次数。
- consumer group 的 topic/partition/current offset/end offset/lag。
- retry/DLQ 数量。
- Redis stock/buyers、MySQL stock/claims/orders，明确读数不是跨系统原子快照。
- 所有错误只输出稳定分类，不打印密码、DSN 或完整消息正文。

## 性能目标

不预设固定 QPS。相同环境、库存、用户、请求数与并发度下比较 v0.3 sync 和 v0.4 async：

- 入口 QPS、P50/P95/P99、HTTP 202 数。
- MySQL Purchase 调用数和峰值并发；async 峰值并发必须受消费者配置上限约束。
- Kafka 峰值 lag、停止生产后的排空时间和订单最终完成数。
- 最终 Redis buyers、job、orders、claims 均不超过初始库存。
- 不宣称总 SQL 数一定下降；v0.4 增加了 job 写入，目标是削平重事务峰值而不是减少所有 SQL。

## 测试策略

- 单元测试：配置、消息校验、job 状态、错误分类、退避和 HTTP 映射。
- MySQL 集成测试：EnsureJob 幂等、状态条件更新、用户结果查询、migration 往返。
- 真实 Kafka 集成测试：发布/消费、重复消息、retry、DLQ、consumer group lag。
- MySQL+Redis+Kafka 端到端：1000 用户/100 库存、同用户 100 并发、最终不超卖不重复。
- 故障测试：Kafka 不可用后恢复、发布确认后标记前崩溃、MySQL 提交后 offset 前崩溃、poison message、消费者停机积压与恢复。
- 并发测试必须执行 race detector；阶段门禁缺少真实 MySQL、Redis 或 Kafka 地址时必须失败，不能静默 skip。
- 全量 `go vet`、migration `up/down/up`、`git diff --check` 和技术边界扫描。

## 注释要求

关键 Go/SQL/消息处理代码必须使用中文解释“为什么”和失败边界，至少覆盖：

- 202 是持久化排队承诺，不是订单成功。
- Redis 与 job 表非原子，失败后为何保留预留并复用 order_no。
- broker ack 与 job 标记之间为何会重复发布。
- 数据库提交与 offset 提交之间为何会重复消费。
- 为什么数据库唯一索引是最终幂等防线。
- 为什么使用 reserved_at 而不是消费时间。
- message key、partition 数与消费者并发的取舍。
- 可重试/不可重试错误分类，retry/DLQ 的确认顺序。
- poison message 为什么不能永久阻塞 partition。
- 优雅退出时在途消息的处理语义。

不要逐行翻译字段赋值、JSON 序列化或显然分支。注释必须能帮助学习者回答“消息为什么会丢/重、如何幂等、为什么扩消费者未必提速”等面试题。
