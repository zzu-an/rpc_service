# v0.3 Redis 秒杀 Spec

## 背景

v0.2 已经用 MySQL 本地事务、条件更新和唯一索引证明了“不超卖、不重复下单”。但所有请求都会进入同一条库存行事务：活动流量远大于库存时，已售罄请求仍会占用数据库连接并争用热点数据。

v0.3 只解决这个问题：在同步下单链路前增加 Redis 准入层，让绝大多数无资格请求在进入 MySQL 前结束，同时保留 v0.2 的数据库正确性防线。

相关架构决策见 `docs/decisions/ADR-002-v03-redis-admission-control.md`。

## 本阶段目标

- 活动开始前把秒杀商品的活动窗口、库存和购买标记写入 Redis。
- 用单个 Lua 脚本原子完成时间窗口、重复购买、库存检查、库存预扣和购买标记写入。
- Redis 售罄后不再调用 MySQL 下单事务，降低热点库存行和连接池压力。
- Redis 与 MySQL 不可能组成原子事务时，定义保守、可重试、可解释的失败语义。
- 用相同 HTTP 工作负载比较 v0.2 MySQL 入口与 v0.3 Redis 入口，不预设性能结论。
- 通过实验掌握缓存穿透、击穿、雪崩、热 key、大 key 和分布式锁的边界。

## 非目标

- 不引入 MQ、异步下单、排队中状态或消息补偿。
- 不拆 RPC 服务，不引入 Protobuf、etcd 或跨服务事务。
- 不实现在线自动对账修复、库存回补、Saga/TCC；这些属于 v0.4/v0.6。
- 不在 Redis 故障时自动回退到 MySQL 秒杀入口。
- 不用分布式锁包住整个下单接口，也不把锁当成 Redis 与 MySQL 的事务替代品。
- 不做系统级限流、熔断、降级、隔离或多级本地缓存；这些属于 v0.7。
- 不宣称 Redis 是订单或库存的最终事实源。

## 允许技术

- Redis（优先复用当前 go-zero 依赖提供的客户端）
- Lua / `EVALSHA`
- Pipeline（只用于预热批量发送，不能替代单商品原子发布）
- `SET key value NX PX` 与 compare-and-delete Lua（只用于独立学习实验）

## 禁止提前引入

- MQ / Outbox / 延迟队列
- gRPC / RPC / etcd
- 分布式事务框架
- Redis 库存分桶、自动扩缩容、系统级限流和本地热点缓存
- 为在线修复而新增数据库表或改变 v0.2 事务含义

## 事实源与职责边界

- MySQL 仍是活动、订单、购买记录和最终可售库存的事实源。
- Redis 只保存短生命周期的活动快照和“进入 MySQL 下单事务的资格”。
- MySQL 的条件库存更新与 `UNIQUE(activity_id, seckill_item_id, user_id)` 继续作为最终正确性防线。
- Redis 预扣成功不等于订单成功；只有 MySQL 事务提交后才能返回成功订单。
- Redis 缺失、未预热或不可用时必须 fail closed，不能绕过准入层直打 MySQL。

## 管理流程

```text
创建活动（默认 disabled）
  → 添加秒杀商品
  → 启用活动
  → 在 start_at 之前执行预热
  → Redis 对每个商品发布 ready 快照
  → 到达 start_at 后用户可下单
```

- 预热只能读取 MySQL 快照，不能反向修改 MySQL 库存。
- 预热要求活动已启用且尚未开始，避免在线重建覆盖正在变化的购买标记。
- 任一商品预热失败时，该商品保持 not-ready；重试必须幂等。
- 活动停用后应使对应 Redis 快照不可再放行；即使失效传播失败，MySQL 仍会拒绝创建订单。
- Redis 在活动进行中丢失数据时，本阶段停止放行并交由人工处理，不在线猜测或重建购买状态。

## 核心下单流程

```text
HTTP 鉴权身份 + item_id
  → 生成候选 order_no
  → Redis Lua 准入
      ├── NOT_READY / UNAVAILABLE / SOLD_OUT：直接返回，不访问 MySQL 下单事务
      ├── RESERVED：返回本次写入的 order_no
      └── REPLAYED：返回第一次预留保存的同一个 order_no
  → 使用 Lua 返回的 order_no 执行现有 MySQL Purchase
      ├── 已有购买记录：返回原订单，replayed=true
      ├── 首次事务提交：返回新订单
      └── 失败或提交结果未知：保留 Redis 预留，允许同身份重试恢复
```

应用层必须只读取一次 UTC 时间，并把同一时间值交给 Redis 与 MySQL 校验，避免活动边界上两个存储看到不同的“现在”。

## Redis key 契约

每个秒杀商品使用同一 hash tag，保证未来在 Redis Cluster 中执行 Lua 时相关 key 落在同一 slot：

```text
seckill:v03:{item:<item_id>}:state
seckill:v03:{item:<item_id>}:buyers
```

`state` 使用 Hash，至少包含：

- `activity_id`
- `sku_id`
- `status`
- `start_at_ms`
- `end_at_ms`
- `stock`
- `generation`
- `ready`
- `expire_at_ms`

`buyers` 使用 Hash：field 为 `user_id`，value 为首次预留生成的 `order_no`。不能只使用 Set，因为同步重试需要取回同一个订单号来处理“提交结果未知”。

两个 key 必须拥有一致的逻辑生命周期，TTL 设置为活动结束后的短暂保留期，并按 item 计算有界 jitter。jitter 用于错开不同商品的过期时间，不能让同一个商品的 state 与 buyers 生命周期分离。buyers 可在第一次预留时才创建，但 Lua 必须从 state 的 `expire_at_ms` 为它设置相同绝对过期时间。

购买标记数量天然受初始库存约束：只有库存成功减一时才新增 buyer field。实现和测试必须保持这个上界，防止 buyers 演化成无界大 key。

## Lua 原子契约

脚本按固定顺序执行：

1. 校验 state 存在且 ready。
2. 校验活动状态和 `[start_at, end_at)` 时间窗口。
3. 先查询当前用户购买标记；存在时返回原 `order_no`，即使库存已为 0 也允许幂等恢复。
4. 校验库存大于 0。
5. 库存减一并写入 `user_id → order_no`。
6. 返回稳定、可枚举的结果码，不通过字符串错误猜测业务结果。

关键约束：

- 脚本只操作带相同 hash tag 的 key。
- 脚本必须保持 O(1)，禁止扫描 buyers、使用 `KEYS` 或执行不受控循环。
- Go 侧优先加载脚本并使用 `EVALSHA`；遇到 `NOSCRIPT` 只允许受控重载一次。
- Lua 执行期间会阻塞对应 Redis shard，因此脚本注释必须解释为什么保持短小。
- “Redis 单线程”只表示同一 shard 的命令执行具有串行语义，不等于网络、持久化、复制和集群整体都只有一个线程。

## HTTP 契约变化

新增管理接口：

```text
POST /v1/admin/seckill/activities/:activityId/preheat
```

- 需要身份认证和 `seckill:write` 权限。
- 成功响应至少包含 activity ID、预热 item 数和过期时间范围。
- 重复预热在活动开始前必须幂等。

用户下单路径保持不变：

```text
POST /v1/seckill/items/:itemId/orders
```

原有成功响应和 `replayed` 语义保持兼容。新增错误：

- `SECKILL_CACHE_NOT_READY`：商品没有可用预热快照，HTTP 503。
- `SECKILL_TEMPORARILY_UNAVAILABLE`：Redis 调用失败或结果不可判定，HTTP 503。

`SECKILL_UNAVAILABLE` 与 `OUT_OF_STOCK` 保留原有业务含义。

## 配置变化

- 新增 Redis 地址、认证、DB、连接超时和操作超时配置。
- 新增启动期 `Seckill.AdmissionMode`，只允许 `mysql` 或 `redis`，用于可重复的 v0.2/v0.3 对照；v0.3 正式验收使用 `redis`。
- 未知模式或 Redis 模式缺少必要配置时阻止服务启动，不能静默回退 MySQL。
- 密码不得打印到日志或写入验收报告。

## 一致性与失败语义

Redis 和 MySQL 之间没有原子提交，本阶段采用保守预留：

| 场景 | 行为 | 可解释结果 |
|---|---|---|
| Lua 拒绝 | 不访问 MySQL Purchase | 两边库存不变 |
| Lua 成功，MySQL 提交成功 | 返回订单 | 两边各减一次 |
| Lua 成功，MySQL 明确失败 | 保留预留，返回错误 | Redis 库存可能小于 MySQL，造成少卖但不超卖 |
| MySQL Commit 结果未知 | 保留预留，同用户携同一 order_no 重试 | 若已提交则返回原订单；未提交则安全重试 |
| Redis 超时/断连，结果未知 | 不访问 MySQL，不生成第二次预留 | 可能少卖，不能据超时推断脚本未执行 |
| Redis 数据缺失 | fail closed | 不绕过 Redis 打热点数据库 |

本阶段禁止在不确定错误后自动 `INCR` 库存或删除 buyer 标记。否则第一次请求可能已经在 Redis/MySQL 成功，而回滚又重新放出一份资格，形成超卖窗口。

阶段报告必须能说明以下保守不变量：正常预热后，Redis 剩余资格可以低于 MySQL 可售库存，但不能通过自动修复变得高于事实源。差值代表“已预留但未确认提交”的容量；v0.3 只读诊断，不在线修复。

## 缓存风险与热点边界

- 穿透：未知/未预热 item 在 Redis 直接失败，不回源 MySQL Purchase。
- 击穿：购买路径不做懒加载；预热 key 到活动结束后才过期。
- 雪崩：不同 item 使用有界 TTL jitter，配置必须设置超时，禁止无限等待 Redis。
- 热 key：Lua 合并往返并保持 O(1)，但单商品库存仍是单 shard 热点；本阶段必须测量，不用复杂分桶掩盖问题。
- 大 key：buyers 只记录真正获得资格的用户，字段数不得超过初始库存；验收记录内存与字段数量。
- Cluster：key 使用 hash tag 预留兼容性，但本阶段不要求搭建 Redis Cluster。

## 分布式锁学习边界

在 `labs/distributed-lock/` 完成独立实验，至少覆盖：

- `SET key token NX PX ttl` 获取锁。
- token 必须唯一，释放锁使用 Lua compare-and-delete。
- 业务执行超过 TTL、进程暂停或网络分区时，两个持有者可能先后进入临界区。
- fencing token 为什么需要由受保护资源校验。
- Redlock 的假设和争议。

生产秒杀链路不得调用该锁。库存预扣由 Lua 原子状态转换完成，给整个请求加锁会串行化流量，且不能让 Redis 与 MySQL 获得共同事务。

## 性能目标

不预设固定 QPS，使用相同机器、相同数据、相同请求数和并发度做对照。报告至少证明：

- unique 用户且请求量远大于库存时，Redis 模式进入 MySQL Purchase 的首次资格数不超过预热库存。
- 售罄后的请求不访问 MySQL Purchase。
- 记录 MySQL 与 Redis 两种模式的 QPS、P50/P95/P99、错误分类和成功订单数。
- 记录 Redis 各结果码、最终 DB 库存/claim 数、Redis 库存/buyers 数；MySQL Purchase 精确调用数由带 spy 的集成测试证明，HTTP 压测若没有专用观测点必须标为 unavailable，不能用 claim 数冒充调用数。
- 任何性能结论都附硬件、进程配置、Redis 部署方式和原始 JSON 报告。

## 测试策略

- Lua 单元测试：结果码映射、参数校验、`NOSCRIPT` 受控恢复。
- 真实 Redis 集成测试：原子预扣、重复用户、售罄、时间窗口、TTL、并发不变量。
- MySQL + Redis 联合集成测试：订单不超库存、重复请求返回同一订单、提交未知后的重试语义。
- 故障测试：Redis 未启动、连接中断、脚本超时/结果未知、key 丢失。
- 缓存风险测试：不存在 item 不回源、buyers 有界、不同 item TTL 存在 jitter。
- 对照压测：复用 v0.2 HTTP 工作负载，分别运行 mysql/redis admission mode。
- 全量 `go test -race`、`go vet`、migration 往返和阶段技术边界扫描。

需要真实 Redis 或 MySQL 的验收不得静默 skip；缺少显式测试地址时必须使对应阶段门禁失败并给出配置提示。

## 注释要求

关键 Go 与 Lua 代码必须使用中文解释“为什么”和失败边界，至少覆盖：

- 为什么 MySQL 是事实源而 Redis 只是准入层。
- 为什么重复检查必须先于库存检查。
- 为什么 buyer value 保存第一次的 order_no。
- 为什么 Redis 超时不等于 Lua 未执行，以及为何不能盲目补回库存。
- 为什么 Redis 故障时 fail closed 而不是回退 MySQL。
- hash tag、TTL jitter、buyers 上界和 Lua O(1) 的依据。
- `EVALSHA`/`NOSCRIPT` 恢复和脚本超时限制。
- 分布式锁 token、compare-and-delete、TTL 失效与 fencing token。

不要为字段赋值、序列化和显然分支逐行复述；注释应能帮助学习者回答对应的高并发场景题。

## 验收标准

- [ ] ADR-002 已接受，Redis 职责与失败策略没有未决项。
- [ ] 管理员可在活动开始前幂等预热，购买路径不做懒加载。
- [ ] Lua 一次完成检查、扣减、标记，并通过真实 Redis 并发测试。
- [ ] 1000 并发且库存 100 时，订单数与 buyers 数不超过 100，两个库存均不为负。
- [ ] 同一用户 100 并发只消耗一个 Redis 资格并只创建一个订单。
- [ ] Redis 售罄、缺 key 或不可用时不会调用 MySQL Purchase。
- [ ] Redis/DB 差值报告能区分一致、保守预留和不可判定状态，且不在线修复。
- [ ] 缓存穿透/击穿/雪崩/热 key/大 key 的测试或实验结论有文档证据。
- [ ] 分布式锁实验完成，但生产秒杀链路无锁依赖。
- [ ] v0.2/v0.3 同负载压测报告包含原始数据和边界说明。
- [ ] `go test -race ./...`、`go vet ./...`、migration 往返和 `git diff --check` 通过。
- [ ] 阶段扫描确认生产目录没有新增 MQ、业务 RPC、etcd、分布式事务和系统级限流实现；既有 `labs/grpc-deadline` 不属于生产链路。
