# v0.5 阶段验收报告

## 架构结论

v0.5 已从“秒杀单体逐步加组件”切换为微服务治理项目：Redis Stream 仍是 seckill 内部 command queue；
orchestrator 只通过 inventory/order RPC 落单；order 本地事务写 Outbox，再由 Kafka 把已提交订单事实 fan-out
给 notification 与 seckill result projector。没有 Stream→Kafka→RPC 的无收益中转。

这条路线的价值分别可验证：Stream 削平入口峰值；RPC 建立服务所有权与治理边界；Outbox 解决订单事实与
Kafka 发布的可靠衔接；不同 Kafka group 让下游独立积压、恢复和扩展。notification 失败不会回滚订单，
projector 停止也不会阻塞 notification。

## 自动验收覆盖

- migration v7→v8 回填历史 reservation 并移除跨服务 FK；v8→v9 建立 Order Outbox；v9→v10 建立通知与消费账本；三步均 up/down/up。
- inventory 1000 并发、库存 100 时严格 100 成功；同用户/同任务 100 次由唯一键收敛。
- Redis Stream 的 XREADGROUP/XAUTOCLAIM、提交后 ACK 前崩溃、PEL 恢复、poison DLQ 和 `reserved_without_order` 有界失败。
- order/outbox 同事务，Kafka 停止只形成 backlog；relay broker ack 后再标记 published。
- notification/projector 使用不同 group：notification 先排空时 projector 保持 QUEUED，恢复后独立追平；重复事件 100 次各自只保留一个业务结果。
- 3 秒慢 RPC、服务停止、50% Unavailable、业务售罄、breaker、etcd 双 endpoint/不可达均有 fault test。
- 日常 11 应用+4 基础设施、治理 13 应用+4 基础设施均真实启动/停止；第二个 order-rpc/notification consumer 摘除后主实例存活。
- gateway 无 DB/Redis/Kafka；六个 RPC 只装配各自 repository/必要 RPC adapter；旧 direct-SQL Stream worker已退役。

## 可复现入口

总门禁为 `make verify-v05`，必须显式提供隔离 MySQL DSN、Redis、Kafka、预建 Outbox 测试 topic 和 etcd。
任一参数缺失会失败，不会把跳过的 integration test 当作阶段通过。`make v05-topology` 输出实例清单，
`make v05-diagnose` 只读输出 endpoint、PEL、Outbox、双 group lag 与 reservation/order 差值。

## 已知边界

- inventory 成功而 order 最终失败会留下 `reserved_without_order`，v0.5 只记录和告警，不自动回补。
- MySQL/Redis/Kafka/etcd 在本阶段各一个实例，只验证应用治理，不宣称基础设施高可用。
- 没有固定 QPS 提升结论；容量必须以目标机器、数据规模和连接池预算重新压测。
- 自动限流、DLQ 人工处置、补偿/对账、支付、可观测平台和容器编排均留给后续里程碑。
