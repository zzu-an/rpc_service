# v0.4.2 双模式压测与跨分支对照

## 比较对象

同一批用户、item、库存、并发数和机器环境下分别运行：

```text
sync          Redis Lua 准入 → 请求内 MySQL 下单 → 200
async-stream  Redis Lua 准入 + XADD → Stream worker → MySQL → 202 + 结果轮询
```

旧参数 `-order-mode async` 会规范化为 `async-stream`。服务配置与压测参数必须一致。
Kafka 报告需要切换到 `codex/v0.4.1-kafka` 后单独运行，不能在当前进程中切换。

## 运行方式

分别以对应的 `Seckill.OrderMode` 启动 API；异步模式还需要启动 Stream worker。
然后用相同参数执行：

```bash
go run ./cmd/loadtest -order-mode sync         -admission redis -scenario unique ...
go run ./cmd/loadtest -order-mode async-stream -admission redis -scenario unique ...
```

异步报告把入口延迟和排空时间分开：HTTP 202 只表示任务已被可靠入口接收，不代表订单
成功；`final_succeeded` 才代表在观测窗口内从 MySQL 读到订单。到达 `drain-timeout` 后仍
为 `QUEUED` 只是未排空，不能直接归类成创建失败。

## Stream 只读诊断

```bash
go run ./cmd/v042check -f etc/store-api.yaml -item <item_id>
```

重点字段：

- `stream.length`：主 Stream 尚未被成功删除的 entry 数量。
- `groups[].pending`：已经投递给消费者但尚未 XACK 的 PEL 数量。
- `groups[].lag`：尚未投递给该 group 的数量；它和 PEL 是两个维度。
- `retry_count`：当前记录过失败次数的消息数量，不是累计失败调用数。
- `dlq_length`：达到最大次数或不可重试的终态消息数。
- `result_count`：仍在 Redis 结果索引生命周期内的 order_no 数量。

命令只读单个 item 的精确 key，不会创建 consumer group、ACK、删除或修复数据。MySQL
和 Redis 是顺序读取，因此库存差值只是诊断线索，不是跨系统原子快照。

## 指标解释与取舍

- 入口 QPS/P99 比较的是接单能力；异步最终成功数和排空耗时比较的是落单能力。
- `async-stream` 的入口不写 MySQL，只写同 slot Redis Stream，但仍需异步创建 MySQL 订单。
- 单 item 的 Lua 与 Stream 同 slot，热点上限仍受单 Redis shard 限制；增加 worker 只提高
  MySQL 消费并发，不会提升该热点 key 的 Redis 串行执行上限。
- `ClaimIdle` 应高于一次 MySQL 处理的合理 P99。设得过小会把仍在执行的消息认领给另一
  consumer；数据库幂等可以防重复订单，但会增加无谓的锁竞争和查询。
- 没有相同环境下的真实报告时，只能说明链路少了一次同步 MySQL 写入，不能宣称固定的
  QPS 提升倍数或 P99 降幅。

## 面试说明

`XREADGROUP ... >` 读取从未投递的新消息，成功投递后消息进入 PEL；worker 在 MySQL
提交后才 XACK。若进程在提交与 XACK 之间崩溃，`XAUTOCLAIM` 会把超时 PEL 转给存活
consumer，MySQL 的 order_no/claim 唯一约束将重复处理收敛为同一笔订单。这是
at-least-once + 幂等，不是 exactly-once。
